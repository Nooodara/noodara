---
title: Error codes
description: Every error code the Noodara API returns, with its HTTP status.
---

Every failed request returns a JSON body shaped like this:

```json
{ "error": "<CODE>", "message": "<text>" }
```

`error` is always one of the codes below. `message` is a short, human-readable description, and
nothing else — no internal detail is ever attached to it.

## HTTP API errors

| Code | HTTP status | Meaning |
|---|---|---|
| `VALIDATION_FAILED` | 400 | The request body does not match the endpoint's schema. |
| `INVALID_CREDENTIAL` | 400 | The submitted SSH credential (password or private key) is invalid, or the current password did not match on a re-authenticated action. |
| `UNAUTHORIZED` | 401 | There is no active session; sign in again. |
| `FORBIDDEN_ORIGIN` | 403 | The request's `Origin` header is not the panel's own origin. |
| `NOT_FOUND` | 404 | The requested resource does not exist. |
| `NAME_TAKEN` | 409 | Another server already uses that name. |
| `HOST_TAKEN` | 409 | Another server already uses that host and port. |
| `SERVER_BUSY` | 409 | The server has a connection or discovery run already in progress. |
| `ALREADY_CONNECTING` | 409 | A connect or discovery run for this server is already in progress. |
| `SERVER_NOT_CONNECTED` | 409 | The action requires the server to be connected first. |
| `NO_PENDING_FINGERPRINT` | 409 | There is no pending host-key fingerprint to trust. |
| `FINGERPRINT_MISMATCH` | 409 | The fingerprint you tried to trust no longer matches what the server has pending. |
| `SERVER_NOT_TRUSTABLE` | 409 | The server is not in a state that can trust a fingerprint right now. |
| `CONFIRMATION_MISMATCH` | 409 | The typed confirmation text did not match what the action required. |
| `QUEUE_UNAVAILABLE` | 503 | The background job queue is unavailable; try again shortly. |
| `SSE_LIMIT_REACHED` | 503 | Too many live event streams are already open. |
| `INTERNAL_ERROR` | 500 | An unexpected server error occurred. |
| `EMAIL_DOMAIN_UNRESOLVABLE` | 400 | The new email address's domain does not resolve. |
| `EMAIL_DOMAIN_CHECK_UNAVAILABLE` | 503 | The email domain check could not run; try again shortly. |
| `REAUTH_LOCKED` | 429 | Too many recent re-authentication attempts; wait before trying again. |
| `SESSION_REVOKED_PASSWORD_CHANGED` | 401 | The session was signed out because the account's password changed. |
| `PROJECT_NAME_TAKEN` | 409 | Another project already uses that name (names are compared case-insensitively). |
| `ENVIRONMENT_NAME_TAKEN` | 409 | The project already has an environment with that name. |
| `PROJECT_NOT_ARCHIVED` | 422 | The project must be archived before it can be deleted. |
| `DELETE_CONFIRMATION_MISMATCH` | 422 | The typed name did not exactly match the name of the resource being deleted. |
| `ENVIRONMENT_NOT_EMPTY` | 409 | `DELETE /api/projects/:projectId/environments/:environmentId` refused: the environment still has services. Delete them first; nothing was changed. |
| `SERVICE_INPUT_INVALID` | 422 | A service field failed validation; `reason` names the rule, such as `REPOSITORY_URL_UNSUPPORTED_SCHEME` or `SERVICE_INPUT_UNSUPPORTED_FIELD`. |
| `SERVICE_NAME_TAKEN` | 409 | The environment already has a service with that name. |
| `PORT_IN_USE` | 409 | The published port is already taken on that server, by another service or by the panel itself. |
| `SERVER_DOCKER_UNAVAILABLE` | 409 | Docker is not installed on the server; services need it. |
| `SERVER_BUILDKIT_UNAVAILABLE` | 409 | Dockerfile (git) services need Docker BuildKit on the server; use an image source or enable BuildKit. |
| `CREDENTIAL_SOURCE_MISMATCH` | 409 | The credential does not fit the service's source: a deploy key needs an ssh repository URL, an HTTPS token an `https://` one, a registry password an image source. |
| `SERVICE_CREDENTIAL_INVALID` | 422 | A credential field failed validation; `reason` names the rule. The submitted value is never echoed back. |
| `SERVER_HAS_SERVICES` | 409 | The server still runs services; `blockingServices` lists them. Move or delete them first. |
| `DEPLOYMENT_IN_PROGRESS` | 409 | The service already has a deployment in progress; wait for it to finish or cancel it. |
| `PROJECT_ARCHIVED` | 409 | The project is archived; unarchive it to deploy its services. |
| `DEPLOYMENT_INPUT_INVALID` | 422 | The deploy request carried a field it does not accept; the body must be empty or `{}`. |
| `DEPLOYMENT_NOT_CANCELLABLE` | 409 | The deployment already ended; only a queued or running deployment can be cancelled. |
| `SERVICE_OPERATION_INVALID` | 422 | The service operation request carried a field it does not accept, or the delete confirmation was missing. |
| `SERVICE_NOT_DEPLOYED` | 409 | The service has never been deployed, so there is no container to stop, restart or remove. |
| `SERVICE_OPERATION_IN_PROGRESS` | 409 | Another stop, restart or remove for this service is already queued; wait for it to finish. |
| `SERVER_UNREACHABLE` | 502 | The panel could not reach the server over SSH (to clean up the service or read its logs); a delete removed nothing. Try again. |
| `SERVICE_CLEANUP_FAILED` | 502 | Removing the service's container, network, images or files on the server failed; nothing was deleted. Try again. |
| `CONTAINER_NOT_FOUND` | 409 | The service has no container on the server, so there are no runtime logs. Deploy the service first. |
| `RUNTIME_LOG_TAIL_INVALID` | 422 | `tail` must be a whole number from 1 to 10000. |
| `RUNTIME_LOG_FOLLOW_LIMIT_REACHED` | 429 | Too many live log streams are open for this server or account. Close one and try again. |
| `RUNTIME_LOGS_FAILED` | 502 | Docker on the server could not read the service logs. Try again or redeploy. |
| `RUNTIME_LOGS_TIMEOUT` | 504 | Reading the service logs timed out. Try again with a smaller `tail`. |

A request the server cannot read at all gets one of three fixed codes with the same body shape:
`MALFORMED_REQUEST` (400, the body is not valid JSON), `PAYLOAD_TOO_LARGE` (413) or
`UNSUPPORTED_MEDIA_TYPE` (415, send `application/json`).

A stop, restart or remove runs in the background after its `202`, so its failures never come back as
an HTTP error. They appear only in the service's activity: `SERVER_UNREACHABLE`,
`SERVER_DOCKER_UNAVAILABLE`, `CONTAINER_NOT_FOUND` (the container is gone; redeploy),
`SERVICE_OPERATION_FAILED` (Docker rejected the operation) or `SERVICE_OPERATION_TIMEOUT`.

A deployment's own failures are recorded on the deployment, not returned as HTTP errors. Two of them
concern the SSH host key of a Git host:

- `GIT_HOST_KEY_MISMATCH`: the Git host offered a key that does not match the one Noodara trusts for
  it. GitHub, GitLab and Bitbucket keys ship with Noodara; any other host's key is stored per service
  on its first SSH clone and checked on every later clone. A changed key is never replaced
  automatically. If the host really rotated its key, verify the new fingerprint with the host's
  operator, then run `noodara services reset-host-key <serviceId>` and deploy again: the next clone
  stores the current key. Changing the service's repository URL to another host also forgets it.
- `GIT_HOST_KEY_UNAVAILABLE`: the Git host's SSH key could not be read, so nothing was cloned.

`ENQUEUE_FAILED`: the deployment was accepted but never reached the job queue (Redis or Postgres was
unreachable at that moment), so nothing ran and the service is unchanged. The worker ends such a
deployment `FAILED` once it has waited past the stale-queue threshold (default 2 minutes) with no
queue job, which frees the service for a new deploy. Check that Redis and Postgres are
reachable, then deploy again.
