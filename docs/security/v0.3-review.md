# Security review v0.3 (task 20-03)

Alcance: receptor de webhooks GitHub, ciclo de vida del secret de webhook, templates de shell
nuevos (`probe.http`, `probe.tcp`, rename `-prev`), almacenamiento de idempotencia y
dependencias nuevas. Checklist: skill `noodara-security`. Fecha: 2026-10-18.

## Hallazgos

| ID | Área | Severidad | Estado | Mitigación / evidencia |
|---|---|---|---|---|
| F1 | API: cuerpo lento | Media | Corregido | Fastify 5 usa `requestTimeout: 0` (nunca): un cliente que enviaba un byte por segundo retenía socket y parser sin límite. `buildApp` fija `requestTimeout` 30 s, pasado también al constructor de Node (si no, `headersTimeout` 60 s queda por encima y el límite no se aplica) y `connectionsCheckingInterval` 1 s. Solo acota la recepción del request: SSE y log-follow no se cortan; `connectionTimeout` sigue en 0. Tests: `apps/control-plane/src/app.test.ts`, `tests/integration/activity/webhook-abuse.test.ts` (408 a ~30 s, sin fila de delivery). |
| F2 | Firma HMAC | — | PASS | Header validado como `sha256=` + 64 hex; HMAC sobre los bytes crudos; `timingSafeEqual` solo con 32/32 bytes; hook desconocido verifica contra un secret dummy (mismo costo). Tests: un único compare de longitud completa por cada prefijo 0..32 y tiempo que no crece con el prefijo (`webhook-abuse.test.ts`). |
| F3 | Cuerpo grande | — | PASS | Límite 1 MiB (`WEBHOOK_BODY_LIMIT_BYTES`): `content-length` declarado mayor da 413 sin leer el cuerpo; chunked da 413 al cruzar el límite; otro content type 415; rate limit por hook e IP en `onRequest`, antes de leer el cuerpo. Nada llega al ingest ni a `webhook_deliveries`. |
| F4 | Replay | — | PASS | El mismo payload firmado con un `X-GitHub-Delivery` nuevo para un SHA ya desplegado responde 200 `already_deployed` y no crea deployment (`canary-deploy.test.ts`, caso 20-03 H1/H2). |
| F5 | Secret de webhook | — | PASS | Cifrado AES-GCM en `credentials`; solo se devuelve en enable/rotate con `Cache-Control: no-store`; rotate y disable borran la fila anterior; el secret rotado da 401; borrar el proyecto borra la credencial. El canary siembra secrets y firmas y no los encuentra en HTTP, SSE, Redis, logs del API y del worker, activity, `webhook_deliveries`, filas de deployments, docker inspect/history ni en el host. |
| F6 | `probe.http` / `probe.tcp` | — | PASS | `env -i`, `bash --noprofile --norc`, `timeout -k`, valores como argumentos posicionales (nunca interpolados), path validado, IP validada, solo se lee una línea de estado de 64 bytes. |
| F7 | Rename `-prev` | — | PASS | Nombres derivados fijos (`noodara-<id>`, `-prev`), `--` antes de los operandos, timeout explícito, nunca `--force`. |
| F8 | Idempotencia | Baja | Aceptado | `Idempotency-Key` se guarda tal cual (lo elige el cliente, no es credencial; 1..255 chars) junto a un fingerprint sha256 de `{action, serviceId, target}`. El body de rollback es estricto: un campo extra (p. ej. un token) da 400 y no se guarda. El canary verifica que el almacenamiento solo contiene las claves sembradas y fingerprints hex de 64. |
| F9 | Dependencias | Moderada | Aceptado | 2026-10-30 (20-10, tras subir better-auth/next/zod/vite/undici): 0 critical, 0 high, 11 moderate, 5 low. Antes: 0 critical, 0 high, 5 moderate (esbuild vía drizzle-kit, solo dev; fast-uri x3 vía fastify/swagger; fastify < 5.12.5 DoS con trailers HTTP/2, HTTP/2 no se usa). Sin dependencias nuevas desde el commit de release v0.2 (`6bac487`); actualizar fastify en v0.4. |
