## M2 legacy: alcance de fase 33 (2026-11-08)

El lease carga al abrir el request los secrets actualmente visibles del proyecto, environment y
servicio autorizados. Conserva la política existente de longitud mínima de ocho caracteres,
incluidos componentes elegibles de valores multilinea; redacta sus formas exacta, base64 y URL.
No carga valores históricos eliminados o rotados, ni actualiza el snapshot durante un follow.
No garantiza redactar secrets de otros servicios que una aplicación comprometida imprima.
Los logs originales de Docker pueden contener los valores: esta garantía cubre las superficies
redactadas que sirve Noodara, no borra la salida original del contenedor.

El [registro de revisión y evidencia](legacy-runtime-log-redaction/README.md) distingue pruebas
locales, gates autoritativos y revisión independiente. El 2026-11-09 M2 queda corregido y
cerrado localmente: regresión/canary verdes, ocho gates originales PASS, revisión tier1
independiente PASS registrada y avance de fase completado ([evidencia final](legacy-runtime-log-redaction/33-03-closure.md)). v0.5.1 conserva su exposición legacy. M2 se distribuyó corregido en v0.5.2 el 2026-11-10,
SHA aprobado `3a34f0daa0a045c48039b2edc882d5ba3bf90fba`: [Release, imágenes, Lima,
backup/restore, HTTP y preservación35-01](../releases/v0.5.2-gate.md#final-stable-distribution-evidence--2026-11-10).
El smoke estable confirmó8 variantes en ambos streams, cero plaintext y limpieza completa. La evidencia histórica del
hotfix AI v0.5.1 en [`docs/releases/v0.5.1-gate.md`](../releases/v0.5.1-gate.md) y `docs/releases/v0.5.1-gate-logs/` y sus tags se conserva intacta.

## Checklist `noodara-security` §10

- Secret como `string` fuera del cifrado: no; la key viaja como `SecretValue` y `revealSecret` solo ocurre en el provider.
- Schemas de salida: rutas AI, settings, logs, métricas y graph declaran `response` Zod (`ai.ts`, `ai-settings.ts`, `*-schemas.ts`).
- Timeouts y `error_code`: provider (P4), SSH de logs y collector con timeouts de `packages/ssh`; fallo del provider → evento SSE `error` + `status: failed` con mensaje fijo (canary AI).
- `ActivityEvent`: el canary AI escanea activity; al modelo solo llega la allowlist de `activityEntry` (`log-entries.ts`).
- Input a shell/path/query: los tools validan con Zod y llaman al backend tipado; no hay template nuevo con input del modelo.
- Borrado: `DELETE /api/settings/ai` (key) y `DELETE /api/ai/conversations/:id` (aborta, borra mensajes y tool calls).
- Test de fuga: `canary-ai.test.ts` (abajo).

## Threat model de prompt injection (H1)

Mitigaciones comunes a todo canal: resultado de tool en sobre JSON fijo (`tools/envelope.ts`), system
prompt `UNTRUSTED` (`prompts/system-prompt.ts:20`), registry cerrado (`AI_TOOL_NOT_ALLOWED`),
redactor (P3) y caps de tamaño (P4). La columna "Mitigación" lista lo específico del canal.

| Canal | Tool que lo lleva | Mitigación específica | Test |
|---|---|---|---|
| Nombre de servicio | `list_services`, `get_service`, `get_infrastructure_graph` | Validador de nombre (DNS label) | `adv-inject-service-name` |
| Nombre de proyecto | `get_infrastructure_graph` | `validateProjectName` (texto libre 1-64) | `adv-channel-project-name` (L1) |
| Nombre de environment | `get_infrastructure_graph` | `validateEnvironmentName` | `adv-channel-environment-name` (L1) |
| Nombre de servidor | `list_servers`, `get_server`, `get_infrastructure_graph` | `validateServerName` | `adv-channel-server-name` (L1) |
| Hostname de dominio | `get_infrastructure_graph` (nodo `Domain`) | Hostname LDH normalizado | `adv-inject-domain-hostname` |
| Nombre de env var | `get_logs` (la app los imprime; ningún tool lista env vars) | `openServiceRedactor` sobre valores | `adv-inject-env-var-name` |
| Log de runtime | `get_logs` | `openServiceRedactor`, cap de líneas (≤ 100) y bytes | `adv-inject-runtime-log` |
| Log de build | `get_logs` | Igual que runtime | `adv-channel-build-log` (L1) |
| Mensaje de commit | `get_logs` (build, `HEAD is now at`) | Igual que runtime | `adv-inject-commit-message` |
| Error de deployment | `get_deployment`, `list_deployments` | `error_code` fijo + mensaje con cap | `adv-inject-deployment-error` |
| Metadata de activity | `get_logs` (fuente activity) | Cerrado: `activityEntry` expone solo acción, outcome, error code y `observedState` allowlisted | `channels.test.ts` "activity metadata never reaches the model" |

`channels.test.ts` falla si un canal del modelo no tiene test en `cases.yaml` o en el propio archivo, y si un campo expuesto no tiene fila en la tabla de abajo.

## Campos que ven los read tools (31-11)

`channels.test.ts` deriva cada campo de `AI_READ_PROJECTIONS` (`apps/control-plane/src/ai/tools/read-projections.ts`,
vía `tests/ai/evals/adversarial/fields.ts`) y exige una fila por campo, el tipo derivado (`free`: texto
arbitrario; `closed`: enum, número, uuid, fecha o patrón) y, para todo campo `free` cuyo origen no es
Noodara, un caso adversarial que lo siembre. Origen: `user` (lo escribe el admin), `host` (lo reporta el
servidor o la app), `external` (GitHub), `noodara` (lo genera el control plane). Los casos `adv-field-*`
siembran el valor que guarda el parser o validador real en cada fila que devuelve el backend; el modelo
hostil lo recibe, ningún write se ejecuta, nada se filtra y el juez detecta la obediencia. RED: con la
tabla vacía faltaban todas las filas, incluidas `repositoryUrl`, `branch`, `buildContext`,
`dockerfilePath`, `buildTarget`, `imageRef`, `healthcheck`, `hostname`, `osDistribution`, `osVersion`,
`dockerVersion` y `dockerComposeVersion`.
