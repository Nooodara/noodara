Fix CR-01 and WR-01 from `.planning/phases/05-ui-web/05-REVIEW.md` (gap-closure round 2 delta): a
real dead end on the server detail screen, plus a stale HOST_KEY_CHANGED banner that outlives a
correct trust. Both live entirely in the host-key trust path that phase 05's own GR-01/GR-02 fixes
made newly reachable, and both were confirmed in code by the orchestrator; CR-01 was also
reproduced live by the user on 2026-09-21.

**CR-01 (critical):** after a host/port edit on a server that is `ERROR`/`HOST_KEY_CHANGED`,
`editServer` (correctly, per GR-02) clears `pendingFingerprint` and `hostFingerprint` but leaves
`status`/`lastErrorCode` untouched. `derivePrimaryAction` (`apps/web/src/lib/detail-state.ts`)
returns `null` for every `ERROR`+`HOST_KEY_CHANGED` row unconditionally, so the toolbar renders no
button; `HostKeyChangedBanner` correctly omits its action when `pendingFingerprint` is `null`, but
still tells the admin to "verify the fingerprint" while showing "Trusted: not available" /
"Observed: not available" -- an instruction with nothing to act on. No control anywhere on the
screen can reconnect the server.

**WR-01 (warning):** `trustFingerprint`'s successful-promote `UPDATE` sets `hostFingerprint`,
`pendingFingerprint`, `status`, etc., but never `lastErrorCode`. Since `deriveDetailState` checks
`lastErrorCode === 'HOST_KEY_CHANGED'` before anything else, the red banner survives a trust the
admin just correctly completed, until the next connect attempt clears it incidentally.

Fix, per the decided (non-redesign) shape:
(a) `derivePrimaryAction` also considers `pendingFingerprint`: `ERROR`+`HOST_KEY_CHANGED` WITH a
pending fingerprint -> `null` exactly as today (the action lives behind the banner's
type-the-name dialog); WITHOUT a pending fingerprint -> the normal `retryAction()`. The backend
already allows `ERROR -> CONNECTING`, and with `hostFingerprint` null the next connect is a clean
TOFU first capture (already proven by 05-40's own integration test).
(b) `HostKeyChangedBanner` shows calm English copy (no fingerprint-verification instruction) when
BOTH `hostFingerprint` and `pendingFingerprint` are null, hiding the Trusted/Observed rows and the
`ssh-keygen` command in that state only -- every other state stays byte-identical.
(c) `trustFingerprint`'s promote `UPDATE` adds `lastErrorCode: null` to its `.set({...})`. The
pre-`UPDATE` guard (`row.lastErrorCode !== 'HOST_KEY_CHANGED'`) and the `WHERE` predicate
(`eq(servers.lastErrorCode, 'HOST_KEY_CHANGED')`) stay exactly as they are -- a `WHERE` evaluates
against the pre-update row, so clearing the column in `SET` does not weaken it.

Explicitly **not** in scope: `editServer`'s own status/`lastErrorCode` handling, and anything in
`packages/domain`'s transitions.

Purpose: close a genuine user-facing dead end (confirmed live) and a self-inconsistent post-trust
state, both reachable through ordinary product use, with regression coverage that did not exist
before.

Output: `derivePrimaryAction` and `HostKeyChangedBanner` updated with unit coverage; `trustFingerprint`
updated with integration coverage; the two affected `tests/e2e/host-key.spec.ts` scenarios extended
to prove both fixes against a real backend.
