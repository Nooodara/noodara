    3. `pendingFingerprint === null` -> NO_PENDING_FINGERPRINT.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin trust decision -> pinned host key | Promoting a pending fingerprint permanently re-establishes trust for a host that failed verification |
| future routes/workers -> activity_events | Phase 4 code could write audit rows directly, bypassing the services that guarantee metadata discipline |

## STRIDE Threat Register

| Threat ID | Category | Description | Asset | Severity | Disposition | Mitigation (task) |
|---|---|---|---|---|---|---|
| T-3-07 | Spoofing | A changed host key is promoted implicitly (e.g. by a retry or an edit) instead of by an explicit admin decision | `servers.host_fingerprint` | high | mitigate | Task 2 makes promotion a dedicated service gated on a non-null pending fingerprint and the reason-gated `ERROR -> PENDING` edge; `connectAndDiscover` never promotes (plan 03-08's grep criteria) |
| T-3-09 | Repudiation | Trust is re-established with no record of which fingerprint replaced which | audit trail | high | mitigate | Task 2's `server.fingerprint_trusted` event carrying both fingerprints, asserted deep-equal |
| T-3-06 | Tampering | Trust is promoted while a connect job is in flight | `servers` | medium | mitigate | `SELECT ... FOR UPDATE` + `SERVER_BUSY` |
| T-3-08 | Tampering / Repudiation | A route or worker writes activity events directly with undisciplined metadata, or skips writing them entirely | `activity_events` integrity | high | mitigate | Task 3's static boundary test, including the non-vacuity and direct-insert cases |
| T-3-32 | Tampering | The boundary test silently scans nothing (bad glob) and passes forever | ACT-01 enforcement | medium | mitigate | Task 3's explicit minimum-file-count and legitimate-importer assertions |
</threat_model>
