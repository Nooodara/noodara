<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin-supplied credential -> control plane | A private key / password arrives as already-parsed service input and must be validated before it is encrypted and stored |
| apps/control-plane -> packages/ssh | The only supported coupling is the package's `.` entrypoint; reaching into internals would let a service drift from the adapter's rules |

## STRIDE Threat Register

| Threat ID | Category | Description | Asset | Severity | Disposition | Mitigation (task) |
|---|---|---|---|---|---|---|
| T-3-10 | Tampering | A weak or unsupported private key (RSA < 2048, unsupported type, malformed PEM) is accepted and persisted, only failing much later at first connect | `credentials.encrypted_value`, server reachability | high | mitigate | Task 2 exposes `loadPrivateKey` so plan 03-04 validates with the same `ACCEPTED_KEY_TYPES`/`RSA_MIN_MODULUS_BITS` rules the adapter enforces; proven by the new `@noodara/ssh` surface test and by 03-04's credential-store tests |
| T-3-15 | Tampering | A service duplicates key-validation rules locally, which then silently drift from the adapter's rules | key acceptance policy | medium | mitigate | Task 2's additive export + the exact-match `EXPECTED_RUNTIME_EXPORTS` guard make the shared function the only sanctioned path; `packages/ssh/src/boundary.test.ts` keeps ssh2 contained |
| T-3-16 | Repudiation | Operators reason about `CONNECTED` as "a live session exists" and misread the audit trail / server list | server status semantics | low | mitigate | Task 3 records D-03 semantics in the committed doc |
</threat_model>
