      `export type RegisterServerFailureCode = 'VALIDATION_FAILED' | 'INVALID_CREDENTIAL' | 'NAME_TAKEN' | 'HOST_TAKEN';`
      `export type RegisterServerResult = { readonly ok: true; readonly server: ServerView } | { readonly ok: false; readonly code: RegisterServerFailureCode; readonly message: string };`
      `export async function registerServer(deps: ServerServicesDeps, input: RegisterServerInput): Promise<RegisterServerResult>`

    Order of operations:
    1. Apply defaults: `sshPort ?? 22`, `sshUser ?? 'root'` (SERV-01's stated defaults).
    2. Validate name/host/port/user with the four domain validators; on the first failure return
       `{ ok: false, code: 'VALIDATION_FAILED', message: <validator message> }`. Do not write new
       regexes and do not lowercase the name for the caller — `validateServerName` rejects
       uppercase rather than normalising it.
    3. `encodeCredential(input.credential, { key: deps.masterKeys.current, version: await currentKeyVersion(deps.db) }, deps.redactor)`;
       on `{ ok: false }` return `{ ok: false, code: 'INVALID_CREDENTIAL', message }`.
    4. Open `deps.db.transaction(async (tx) => { ... })` and inside it:
       a. pre-check `select id from servers where lower(name) = lower($name)` -> `NAME_TAKEN`;
       b. pre-check `select id from servers where host = $host and ssh_port = $port` -> `HOST_TAKEN`;
       c. insert the `credentials` row (type/encryptedValue/keyVersion from step 3), returning its id;
       d. insert the `servers` row with `status: 'PENDING'` (the column default — never assign a
          status through any path other than the default or `transition()`), `credentialId` from (c),
          returning the full row;
       e. `writeActivityEvent(tx, { actorType: input.actor.type, actorId: input.actor.type === 'user' ? input.actor.id : null, entityType: 'server', entityId: server.id, action: 'server.created', outcome: 'success', metadata: { name, host, sshPort, sshUser, credentialType } }, deps.now())`;
       f. return `{ ok: true, server: toServerView(server, credentialType) }`.
    5. Wrap the transaction body's inserts so a Postgres unique violation (`error.code === '23505'`)
       is translated by constraint name: `servers_name_lower_unique_idx` -> `NAME_TAKEN`,
       `servers_host_port_unique_idx` -> `HOST_TAKEN` (D-10's safety net behind the pre-checks).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| already-parsed service input -> domain validators | Name/host/port/user are untrusted until the domain validators accept them |
| service -> credentials table | Raw credential material crosses into storage exactly once, already enveloped |
| service -> activity_events | Registration metadata crosses into the audit trail |

## STRIDE Threat Register

| Threat ID | Category | Description | Asset | Severity | Disposition | Mitigation (task) |
|---|---|---|---|---|---|---|
| T-3-01 | Information Disclosure | The registration result leaks the credential or its id | service result | high | mitigate | Task 2 returns `toServerView(...)` only; Task 1 asserts the result JSON is free of the raw secret and of `credentialId` |
| T-3-13 | Tampering | A case-variant or duplicate host:port registration creates a second identity for the same machine | `servers` identity | high | mitigate | Task 2's in-transaction pre-checks plus the 23505 constraint-name translation over plan 03-03's unique indexes |
| T-3-23 | Tampering | A failed registration leaves an orphan encrypted credential row | `credentials` | medium | mitigate | All writes live inside one `db.transaction`; Task 1 asserts zero orphan rows after every failure case |
| T-3-24 | Tampering | Command metacharacters in a server name reach an SSH command template | remote shell | high | mitigate | `validateServerName`'s slug pattern rejects them at the domain layer; phase 2's frozen allowlist means server-provided values never reach a template regardless |
| T-3-02 | Information Disclosure | Registration metadata carries the credential | `activity_events.metadata` | high | mitigate | D-16 metadata allowlist in Task 2 plus `buildActivityEvent`'s `SensitiveMetadataError` guard; asserted deep-equal in Task 1 |
| T-3-25 | Repudiation | A server appears with no record of who created it | audit trail | medium | mitigate | D-17 actor propagation asserted for both `user` and `system` actors |
</threat_model>
