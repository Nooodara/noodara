# Phase 7: Identidad y brand kit - Research

**Researched:** 2026-09-22
**Domain:** Code-generated SVG brand identity (monogram + wordmark), theme-aware application in a Next.js 16 App Router shell, static asset export for a future consumer package, human-approval workflow
**Confidence:** HIGH (repo facts, Next.js file conventions, tokenscss/gate mechanics — all verified against the real repo or Context7) / MEDIUM (raster pipeline package choice — verified on npm registry, not via Context7 official docs) / LOW (none — no claim rests solely on unverified web search)

## Summary

This phase has almost no "which library" research — `docs/ui-build-prompt.md` and `07-CONTEXT.md` already lock the visual method (code-built SVG on a 24-unit grid, `currentColor` in-app, two static SVGs for README/site, one blue favicon tile). What actually needs researching to plan this well is **mechanical**: how the existing repo's conventions (token gate, package exports, Next.js 16 file-based metadata, the `install-docs-accuracy.test.ts` exactness-test pattern, the Playwright E2E stack fixture) constrain *where* the brand components live, *how* static assets get generated and verified without drifting from the single source of truth, and *how* the human-approval step (D-13..D-17) gets staged without becoming an un-scriptable manual chore.

Three findings change how the planner should sequence work. First, `scripts/check-ui-safety.mjs`'s hex/rgb-literal gate only scans `.ts`, `.tsx` and `.css` files under `apps/web/src` and `packages/ui/src` — it never touches `.svg` files anywhere, so the favicon's hardcoded `#0071e3` tile needs no allowlist edit; it simply must live in a static `.svg`/`.png`/`.ico` file, never inlined as a `.tsx` component with a hex literal. Second, Next.js 16's file-based icon convention (`app/icon.svg`, `app/apple-icon.png`, `app/opengraph-image.png`, `app/favicon.ico`, `app/manifest.ts`) requires the actual bytes to be physically present under `apps/web/src/app/` — there is no workspace-import escape hatch for these specific reserved filenames, so "packages/ui exports assets, apps/web consumes without copying" (Phase 10's requirement) cannot literally mean zero bytes duplicated for `apps/web`'s own favicon; it means **one generation source, one scripted sync step**, not manual copy-paste. Third, the D-14 requirement to review the favicon "in the browser tab" cannot be produced by an automated screenshot (`page.screenshot()` never captures OS/browser chrome) — the plan must route that one surface through a human manually opening the dev URL, not through a script.

**Primary recommendation:** Build a single pure geometry module (`packages/ui/src/brand/geometry.ts`: grid=24 constant, stroke/radius constants, path-builder helpers) and three React components (`Logo`, `Wordmark`, `Lockup`) that consume it and render `currentColor` SVG — this is the in-app source of truth. Generate every static export (light/dark ink SVGs, favicon tile SVG/PNG/ICO, apple-touch-icon, PWA icons, OG image) from that *same* module via a Node/`tsx` script (`scripts/generate-brand-assets.mjs`, mirroring `scripts/capture-discovery-fixtures.mjs`'s existing pattern) using `sharp` for SVG→PNG rasterization and `png-to-ico` for the multi-resolution `.ico` container; commit the generated files under `packages/ui/brand/` and verify them with a Vitest exactness test (mirroring `tests/unit/docs/install-docs-accuracy.test.ts`) that regenerates in-memory and fails on any diff. Expose them via `packages/ui/package.json`'s existing static-file-export pattern (`"./tokens.css"` precedent → add `"./brand/*"`). `apps/web` gets a tiny `predev`/`prebuild` sync script that copies the already-generated bytes into `apps/web/src/app/{favicon.ico,icon.svg,apple-icon.png,opengraph-image.png}` because Next's route-metadata file convention requires physical local presence — this is the one place a "copy" is unavoidable, and it is scripted, not manual, so `packages/ui/brand/` stays the only source a human ever edits or regenerates.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| `sharp` for SVG→PNG | `@resvg/resvg-js` (2.6.2, napi/WASM, `yisibl/resvg-js`) | Smaller footprint, Rust-based `resvg` renderer with arguably more spec-correct SVG parsing, but a second, less ubiquitous dependency for a capability `sharp` already covers well; only worth it if `sharp`'s librsvg-based SVG rasterization mishandles a specific path/arc construct this brand's geometry needs (unlikely for pure fills/arcs — verify by rendering one concept early, see Open Questions) |
| `sharp` + `png-to-ico` for favicons | A Playwright script that screenshots an HTML page at fixed pixel sizes | Playwright is already a devDependency (zero new install), but screenshot-based rasterization is imprecise at small sizes (16/32px) without careful `deviceScaleFactor`/DPI handling, and cannot easily produce a true multi-resolution `.ico`; reserve Playwright for what it is already used for in this repo — full-page/component screenshots for the human-review step, not pixel-exact icon generation |
| Generated static `.ico`/`.png` files under `app/` | Dynamic `app/icon.tsx` / `app/apple-icon.tsx` using `next/og`'s `ImageResponse` | `ImageResponse` can import the shared geometry module directly at request/build time with zero physical file duplication, but it re-renders on every build/request (edge runtime by default), adds `ImageResponse`'s own JSX-subset constraints, and produces output that is harder to pin down byte-for-byte for the exactness test; committed static files (regenerated by a script, verified by a test) are simpler and match `docs/install.md`'s existing "generate once, verify with a test" pattern |
| Is `.ico` needed at all in 2026 | `app/icon.svg` alone (no `favicon.ico`) | Chromium/Firefox/Safari all accept SVG favicons today, but `favicon.ico` remains the fallback every browser (and RSS readers, some bookmarklets, IE-descended enterprise browsers) checks first at `/favicon.ico` regardless of `<link>` tags — keep both; `.ico` costs one extra generation step, not extra design work, since it packs the same PNG renders `png-to-ico` already produces |

### Pattern 1: Single geometry source, two consumers (component + generator script)

**What:** One pure TS module defines the monogram/wordmark path data (constants for the 24-unit grid, stroke width, aperture radius). A React component renders it live with `currentColor`; a Node script renders the exact same component tree via `renderToStaticMarkup` to produce every static export. Neither ever duplicates path coordinates.

**When to use:** Any time a visual asset needs both a live, theme-aware in-app form and a static, portable export (README, favicon, OG image) — this is D-10's explicit requirement ("nunca dibujados aparte").

**Example:**
```typescript
// packages/ui/src/brand/geometry.ts — Source: repo convention (mirrors packages/domain's
// pure-module discipline: no I/O, importable by both React runtime and a plain Node script)
export const GRID = 24; // 24-unit design grid (D-15)
export const STROKE = 2.5; // grid units
export const APERTURE_RADIUS = 6; // grid units — shared by the monogram opening and the "oo" (D-08)

export function monogramPath(): string {
  // Fill-only outline (not a `stroke`-drawn path) — avoids stroke-width scaling artifacts at
  // 16px and keeps every coordinate on integer grid units for crisp rendering (see Common
  // Pitfalls #4). Concrete arc/angle values are this phase's Claude's Discretion area (D-03/D-15).
  return `M ...`;
}
```

```tsx
// packages/ui/src/brand/Logo.tsx
import { monogramPath } from './geometry.js';

export interface LogoProps {
  readonly 'aria-hidden'?: boolean;
  readonly title?: string; // only set when the mark stands alone with no adjacent visible text
}

export function Logo({ 'aria-hidden': ariaHidden, title }: LogoProps) {
  return (
    <svg viewBox="0 0 24 24" fill="currentColor" role={title ? 'img' : undefined} aria-hidden={ariaHidden}>
      {title ? <title>{title}</title> : null}
      <path d={monogramPath()} />

}
```

### Pattern 2: Two static SVGs per lockup (light ink, dark ink), never a third "auto" file

**What:** For contexts with no CSS theming access (README, OG image, any non-app consumer), export exactly two pre-colored SVGs — one with `ink` (light theme, dark strokes on transparent background) and one with `ink` (dark theme, light strokes) baked in as a literal fill color, generated from the same component with a `color` prop override instead of `currentColor`.

**When to use:** Any static, non-CSS-themed consumption surface (D-10).

**Example (README):**
```html
<!-- Source: GitHub's documented <picture>/prefers-color-scheme support (WebSearch, cross-checked
     against github.blog's own "How to make your images in Markdown on GitHub adjust for dark
     mode and light mode" post) -->
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="packages/ui/brand/lockup-dark.svg">
  <source media="(prefers-color-scheme: light)" srcset="packages/ui/brand/lockup-light.svg">
  <img alt="Noodara" src="packages/ui/brand/lockup-light.svg" width="220">
</picture>
```
The historical `#gh-dark-mode-only` / `#gh-light-mode-only` URL-fragment trick is a documented, simpler-but-less-portable alternative (it does not work in gists or on github.dev per the sources found); prefer `<picture>` since it degrades gracefully to the `<img>` fallback everywhere.

### Pattern 3: Next.js 16 file-based icon metadata, not the JS `metadata.icons` object

**What:** Place `favicon.ico`, `icon.svg`, `apple-icon.png`, `opengraph-image.png` directly under `apps/web/src/app/` (root, since these apply site-wide) instead of hand-writing a `metadata.icons` object in `layout.tsx`. Next.js auto-discovers these reserved filenames and injects the correct `<link>`/`<meta>` tags — confirmed via Context7 against Next.js 16.2.9 docs (`app-icons.mdx`, `project-structure.mdx`): `favicon` must be `.ico` at the top level of `app/`; `icon` accepts `.ico/.jpg/.jpeg/.png/.svg` and can be placed anywhere under `app/**`; `apple-icon` accepts `.jpg/.jpeg/.png`.

**When to use:** BRAND-02's favicon/apple-touch-icon requirement.

**Example:**
```typescript
// apps/web/src/app/manifest.ts — Source: Context7 /vercel/next.js/v16.2.9,
// docs/01-app/03-api-reference/03-file-conventions/01-metadata/manifest.mdx
import type { MetadataRoute } from 'next';

export default function manifest(): MetadataRoute.Manifest {
  return {
    name: 'Noodara',
    short_name: 'Noodara',
    start_url: '/',
    display: 'standalone',
    background_color: '#161618', // canvas dark — literal is acceptable here: manifest.ts is not
    theme_color: '#0071e3',       // scanned by check-ui-safety (only .ts/.tsx/.css under
                                   // apps/web/src and packages/ui/src with the (ts|tsx|css) glob —
                                   // manifest.ts DOES match that glob, so verify at implementation
                                   // time whether this needs a token import instead; see Open
                                   // Questions.
    icons: [
      { src: '/icon-192.png', sizes: '192x192', type: 'image/png' },
      { src: '/icon-512.png', sizes: '512x512', type: 'image/png' },
    ],
  };
}
```
**Because `metadata.icons` also supports a `media` key (`{ url: '/icon-dark.png', media: '(prefers-color-scheme: dark)' }`), a genuine question the planner should close explicitly: D-11 states the favicon tile is `accent-fill` blue in both themes ("la única superficie donde la marca lleva azul", same hex both themes per `tokens.css`) — so a single icon file is correct and no dark/light favicon split is needed. This is a **confirmed, not assumed**, reading of D-11 cross-referenced with `tokens.css`'s `--accent-fill: #0071e3` being identical under both `:root` and `[data-theme="dark"]`.**

### Pattern 4: Static asset export via package.json `exports`, not a build artifact copy

**What:** Extend `packages/ui/package.json`'s existing `"exports"` map (which already exposes `"./tokens.css"` and `"./theme.css"` as raw static files with no build step) with `"./brand/*": "./brand/*"`. Any consumer resolves `@noodara/ui/brand/lockup-dark.svg` to the real file on disk via the pnpm workspace symlink — no copy needed for any consumer that does a plain file read / `<img src>` reference to a resolved path, or a build-time static `import`.

**When to use:** Phase 10's `apps/site` consumption (BRAND-02's "sin copiar archivos" success criterion), and any future consumer.

**Caveat (verified via Context7):** a plain Next.js `import x from '@noodara/ui/brand/foo.svg'` does **not** automatically return a usable URL — Next.js's built-in static-import asset handling (the `next/image` `StaticImageData` path) covers common raster formats, but `.svg` specifically requires an explicit Turbopack rule (`turbopack: { rules: { '*.svg': { type: 'asset' } } }` in `next.config.ts`) to be importable as a URL string at all; without it, importing a `.svg` either errors or (with certain loaders) returns a React component instead of a URL, which is the wrong shape for `<img src>`/`next/image`. This is a **Phase-10-relevant finding to record now**, since Phase 7 must decide whether `apps/web`'s own consumption of `packages/ui/brand/*` goes through file-convention copies only (recommended — sidesteps the Turbopack config entirely) while Phase 10 is left to add the Turbopack rule if `apps/site` wants to `import` these files directly, or use plain `<img src="/brand/lockup-dark.svg">` against a copy in its own `public/` (same predev-sync pattern as `apps/web`).

### Anti-Patterns to Avoid
- **Hand-drawing a second "static" SVG that isn't generated from the component:** violates D-10 explicitly ("generados desde la misma fuente, nunca dibujados aparte") and creates silent drift the moment the geometry constants change.
- **Writing the favicon tile's `#0071e3` fill into a `.tsx` React component:** would trip `check-ui-safety.mjs`'s hex-literal gate (scans `.tsx` under `packages/ui/src`) — the accent tile must only exist as a generated static `.svg`/`.png`/`.ico` file, never as JSX with an inline hex.
- **Treating the "screenshot the favicon in the browser tab" review step as scriptable:** Playwright's `page.screenshot()` captures page content only, never OS/browser chrome (tab bar, favicon). Plan this as a manual `checkpoint:human-verify` instruction ("open http://localhost:3000 yourself and look at the tab"), not an automated capture.
- **Regenerating `packages/ui/brand/*` on every `next build`/`pnpm build`:** these are checked-in, human-reviewed, approved assets (D-17) — regenerate only via the explicit script, verified by a test that fails on drift, exactly like `docs/install.md` is hand-maintained-but-verified rather than auto-generated on every build.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| SVG → PNG rasterization at exact pixel sizes | A custom canvas-based or Playwright-screenshot rasterizer | `sharp` (`sharp(svgBuffer).resize(w, h).png().toBuffer()`) | Pixel-accurate, DPI-correct, handles the full SVG spec surface (arcs, transforms) via libvips/librsvg; a Playwright-screenshot rasterizer would need careful `deviceScaleFactor` math to avoid blur at 16px and cannot easily target arbitrary non-viewport pixel dimensions |
| Packing PNGs into a real multi-resolution `.ico` | Hand-rolling the ICO binary container format (header + directory entries + PNG/BMP payloads) | `png-to-ico` | The ICO format's header/directory-entry byte layout is a well-known, easy-to-get-subtly-wrong binary format (entry count, per-entry width/height-as-0-means-256 quirk, offset table) — a tiny, stable, single-purpose library exists specifically because everyone gets this wrong the first time |
| GitHub README dark/light image switching | A build step that swaps `README.md` content per some external signal | `<picture>` + `prefers-color-scheme` media queries (native GitHub Markdown/HTML support) | Zero build step, zero JS, works in gists/github.dev too when done via `<picture>` (confirmed less portable with the `#gh-dark-mode-only` fragment hack) |
| SVG output normalization | Hand-writing regex to strip `renderToStaticMarkup`'s output noise | `svgo` (optional, only if actually noisy) | `renderToStaticMarkup` output is already reasonably clean (no XML declaration, no React-internal attributes); only reach for `svgo` if a concrete cleanliness problem shows up — don't add a dependency preemptively (see Open Questions) |

**Key insight:** every "don't hand-roll" item in this phase is a well-solved binary/text-format problem (raster image, ICO container, conditional Markdown image) with a small, stable, single-purpose library already available — the actual creative work (the geometry, the concept, the meaning) is explicitly *not* delegated to any library or generator per D-15 ("no hay herramienta gráfica ni generación de imágenes en el flujo").

## Common Pitfalls

### Pitfall 1: Assuming the token gate needs a hex-literal allowlist entry for the favicon
**What goes wrong:** A planner assumes `scripts/check-ui-safety.mjs`'s "zero hex colour literals outside `packages/ui/tokens.css`" gate will fail on the favicon's `#0071e3` fill and plans a task to edit the gate's allowlist/scan-file-list.
**Why it happens:** The gate's stated purpose ("zero hex colour literals outside tokens.css") sounds absolute, and the favicon genuinely does need a hardcoded hex value (D-11: the one place the mark carries blue).
**How to avoid:** Read the gate's actual file selection (`TSX_GLOBS = ['apps/web/src', 'packages/ui/src']`, filtered to `/\.(ts|tsx|css)$/`) — it never includes `.svg`, `.ico`, or `.png` files, and the favicon tile lives only as a generated static `.svg`/raster file, never as `.tsx`. No gate edit is needed as long as the favicon color is never written into a `.ts`/`.tsx`/`.css` file (verified directly by reading `scripts/check-ui-safety.mjs` in full this session).
**Warning signs:** A plan task titled "update check-ui-safety allowlist for brand colors" — this is very likely unnecessary; verify by running `pnpm check:ui-safety` after adding the generated files, not by editing the gate defensively.

### Pitfall 2: Trying to automate the "favicon in the browser tab" review screenshot
**What goes wrong:** A plan task tries to have Playwright "screenshot the favicon in the tab" as part of the automated brand-review capture script, alongside the rail/sidebar/login/setup screenshots.
**Why it happens:** D-14 explicitly lists "favicon en la pestaña del navegador" as one of the review surfaces, and the rest of the review is scripted, so it's natural to assume this is scriptable too.
**How to avoid:** Playwright's screenshot API captures page/viewport content, never the browser's own chrome (tab strip, title, favicon rendering) — this is a hard platform limitation, not a configuration gap. Plan this as an explicit manual step: the human opens the real dev URL in their own browser at approval time and looks at the tab directly (or the plan mocks a "browser tab" visual swatch — an HTML strip with the icon + page title styled to resemble a tab — inside the static brand-board page, clearly labeled as a simulation, for the other automated screenshots' context).
**Warning signs:** A task or acceptance criterion that says "Playwright captures the favicon in both themes" without naming which surface (tab vs. in-page) it means.

### Pitfall 3: `apps/web`'s favicon/apple-icon files silently going stale relative to `packages/ui/brand/`
**What goes wrong:** The brand kit changes (a D-16 adjustment round), `packages/ui/brand/*` regenerates correctly, but `apps/web/src/app/{favicon.ico,icon.svg,apple-icon.png,opengraph-image.png}` are hand-copied once and never re-synced, so the app silently serves an outdated icon after the "final" approved version replaces an earlier draft.
**Why it happens:** Next.js's file-convention icons require physical local presence (verified via Context7 — no workspace-import path exists for these exact reserved filenames), which tempts a one-time manual `cp` instead of a repeatable script.
**How to avoid:** Write the sync as a `predev`/`prebuild` npm script in `apps/web/package.json` (not a one-off manual copy), so it re-runs on every dev/build and can never drift silently. Add a Vitest test that byte-compares `apps/web/src/app/favicon.ico` etc. against `packages/ui/brand/favicon.ico` (same exactness-test pattern as the brand-assets-accuracy test) so CI catches drift even if someone forgets to run the sync script locally.
**Warning signs:** `apps/web/src/app/apple-icon.png`'s git history shows a manual edit/replace commit instead of a "ran the sync script" commit; the file's bytes differ from `packages/ui/brand/apple-touch-icon.png` in CI.

### Pitfall 4: Stroke-based paths causing blur/inconsistency at 16px
**What goes wrong:** If the monogram is built with `stroke` (an outline drawn along a path) rather than `fill` (a solid filled shape), `stroke-width` scaling behaves inconsistently across the different render contexts (in-app `currentColor` SVG at 20px icon size vs. a 16×16 favicon PNG vs. a 256px brand-board scale) — sub-pixel stroke widths at small sizes look inconsistent or blurry depending on the rasterizer's anti-aliasing.
**Why it happens:** Grid-based logo construction (D-15) is often prototyped with `stroke` because it's the more intuitive way to sketch a monoline mark, but production marks that must read at 16px are conventionally built as filled outlines (the stroke "baked into" the path geometry as a closed shape) precisely to avoid this.
**How to avoid:** Build the monogram/wordmark paths as filled shapes (`fill="currentColor"`, `fill-rule` as needed for the aperture cutout) with the stroke width baked into the path's own geometry, not as a live `stroke` on a thin centerline path. Keep every path coordinate on integer grid units (24-unit grid) so `sharp`'s rasterization and the browser's own SVG renderer both anti-alias predictably at 16px. `[ASSUMED]` — this is established icon-design practice, not verified against an official source this session; flag for the brand-kit construction sheet to state explicitly and for the 16px legibility check in the review script to confirm empirically.
**Warning signs:** The monogram looks crisp at 256px in the brand board but fuzzy/uneven in the 64px rail or the browser tab favicon.

### Pitfall 5: Apple touch icon with alpha transparency
**What goes wrong:** `apple-icon.png` (180×180) rendered with a transparent background can show unpredictable fill (often black or a default gray) behind the icon on iOS home-screen/Safari-tab-bar contexts, since Apple's touch-icon handling has historically not composited transparency the way a normal `<img>` would.
**Why it happens:** The in-app `Logo` component is inherently transparent-background `currentColor` SVG; exporting the exact same transparent render directly to `apple-icon.png` without compositing an opaque background is the path of least resistance.
**How to avoid:** When generating `apple-icon.png` specifically, composite the monogram onto an opaque `canvas`/`accent-fill`-colored (per D-11, since the favicon family already established the blue-tile convention) background before rasterizing, rather than exporting with alpha. `[ASSUMED]` (long-standing, widely repeated Apple platform guidance; not verified against an official Apple source this session) — flag for empirical confirmation (view the generated PNG's alpha channel; test on an actual iOS device or simulator if available, or accept the conservative always-opaque default).
**Warning signs:** The generated `apple-icon.png` has a non-zero alpha channel when inspected with `sharp`'s own metadata (`sharp(file).metadata().then(m => m.hasAlpha)`).

## Open Questions (RESOLVED)

Resolution recorded at planning time (2026-09-22) — each question is closed by a concrete, testable plan mechanism rather than by further research:

- Q1 (librsvg fidelity) → closed by **07-02 Task 3**: fidelity probe renders an evenodd ring through `sharp` and compares against expectations; on mismatch the task takes the documented Playwright-rasterization branch.
- Q2 (`svgo`) → closed by **07-06 Task 2**: static SVGs are emitted from the geometry module with fixed-precision numbers; `svgo` is not added unless the exactness test surfaces float noise.
- Q3 (`manifest.ts` hex vs. gate) → closed by **07-09 Task 2**: `manifest.ts` reads colours from generated `brand-colors.json` (derived from `tokens.css`), so no hex literal enters a `.ts` file and no gate allowlist edit is permitted; the task runs `pnpm check:ui-safety` immediately after creating the file.

1. **Does `sharp`'s SVG rasterization (via librsvg) faithfully render the specific arc/fill-rule constructs the three monogram concepts will use?**
   - What we know: `sharp` is a mature, widely-used SVG→raster path; librsvg is spec-compliant for standard SVG path/arc/fill-rule syntax.
   - What's unclear: the exact path constructs (arcs meeting at precise angles for the "aperture") haven't been drawn yet — Claude's Discretion area per CONTEXT.md.
   - Recommendation: render the first concept early (even a rough draft) through the full pipeline (`Logo.tsx` → `renderToStaticMarkup` → `sharp` PNG) before committing to the geometry module's final API shape, so any librsvg quirk surfaces before all three concepts are built on top of it.

2. **Does `svgo` earn its place, or is raw `renderToStaticMarkup` output clean enough for `docs/brand/` and the exactness test?**
   - What we know: `renderToStaticMarkup` produces valid, reasonably clean SVG (no XML declaration, no React-internal props) with numeric attribute values exactly as authored in the component.
   - What's unclear: whether path `d` attributes built from floating-point arc math produce visually noisy precision (e.g., `12.000000001`) that would benefit from `svgo`'s number-rounding.
   - Recommendation: skip `svgo` initially; add it only if the generated `packages/ui/brand/*.svg` files show float noise when first produced — cheaper to add later than to integrate speculatively now (Don't Hand-Roll's "don't add a dependency preemptively" guidance applies to tooling choices too).

3. **Does `apps/web/src/app/manifest.ts` need a token-derived or literal hex for `theme_color`/`background_color`?**
   - What we know: the gate's file-selection glob (`/\.(ts|tsx|css)$/` under `apps/web/src`) would technically match `manifest.ts`.
   - What's unclear: whether `manifest.ts`'s hex values (required by the Web App Manifest spec, which has no `var()`/CSS-custom-property concept) will actually be counted by the gate's regex, or whether this is a legitimate, expected exception nobody has hit yet (this repo has never had a `manifest.ts` before).
   - Recommendation: the planner should run `pnpm check:ui-safety` against a draft `manifest.ts` early in the phase and decide then whether the gate needs a scoped exception (matching the existing `tokens.css`-only exclusion pattern) — do not assume either outcome.
