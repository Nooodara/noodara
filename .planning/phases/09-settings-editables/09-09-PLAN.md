<objective>
Ship `POST /api/account/password` (SET-03). It enforces the v0.1 policy, delegates to Better Auth's `changePassword` with `revokeOtherSessions: true` (D-05), keeps the current tab alive by forwarding the rotated cookie, and returns the revoked count (D-06). It also records `account.password_changed` (D-08) and gives revoked sessions a distinguishable 401 that the web heartbeat turns into the `/login?reason=password-changed` redirect (D-07).

Purpose: success criterion 2's backend half.
Background, verified by reading `node_modules/better-auth/dist/api/routes/update-user.mjs` (1.7.4): `changePassword` deletes all of the user's sessions, creates a fresh one, sets its cookie and returns `{ token, user }`. It returns no count, and a wrong password throws `APIError` BAD_REQUEST with code INVALID_PASSWORD. The plan is built around those facts and pins them with a contract test.
Output: markers module, requireSession reason, service, route, integration tests and the canary.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → POST /api/account/password | Carries two passwords; cookie-authenticated |
| Better Auth response → our HTTP response | Contains a fresh session token that must not reach the JSON body |
| revoked session cookie → requireSession | Stale credential presented by another tab or browser |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-04 | Elevation / session persistence | other sessions surviving a password change | high | mitigate | Task 2: Better Auth revokeOtherSessions; the integration test proves B and C get 401 while A's rotated cookie works |
| T-09-05 | Information disclosure | session token in the response body | high | mitigate | Task 2 step 6: the service drops the Better Auth body; ChangePasswordResponseSchema has no token; Task 3 canary scans bodies for the real token |
| T-09-01 | Spoofing / brute force | currentPassword on /password | high | mitigate | Task 2 steps 1 and 4: ReauthGuard check, recordFailure on INVALID_PASSWORD; 429 tested |
| T-09-03 | Information disclosure | activity, logs, errors | high | mitigate | Task 2: metadata { sessions_revoked } only (the 09-01 allowlist); Task 3 canary for passwords, '$argon2' and tokens |
| T-09-10 | Information disclosure | revocation markers | low | mitigate | Task 1: sha256 hashes only, expiring with the session's own expiresAt |
| T-09-11 | Spoofing | fresh session after the change gets a new absolute lifetime | low | accept | Changing the password requires the current password, which is equivalent to a fresh authentication; Better Auth's own design |
| T-09-07 | Tampering (CSRF) | POST /api/account/password | high | mitigate | Registered in the origin-guarded api-scope via 09-06's accountRoutes; cross-origin 403 covered in 09-06's suite for the plugin |
| T-09-27 | Denial of service | marker lookup on every 401 | low | mitigate | Task 1: bounded by withSessionLookupTimeout; a failure degrades to plain UNAUTHORIZED, never 500 |
</threat_model>
