<objective>
Write the production `docker-compose.yml`: the six-service topology the installer brings up, with
the migration one-shot gating `api`/`worker`, a redis healthcheck that actually works, no host
ports on the datastores, and memory limits derived from measurement.

Purpose: this file is the contract between the installer and the images. Two known defects must not
reach it — the dev compose file's redis healthcheck is broken (`$${REDIS_PASSWORD}` with no
`environment:` block on the service, verified by direct read), and a naive one-shot migration
service would be assumed "done forever" when Compose actually re-runs it on every `up`.
Output: `docker-compose.yml`, the same one-line fix applied to `docker-compose.dev.yml`, and an
integration test that stands the whole stack up for real.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet → published host port | `${NOODARA_PORT}:3000` on `web` is the only reachable surface |
| Compose network → datastores | `postgres` and `redis` are reachable only from sibling containers |
| `.env` → Compose interpolation | secrets flow into container environments and into one `command:` array |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-08 | Information Disclosure | `postgres`/`redis` published on the host and reachable from the internet (the dev file publishes both) | mitigate | No `ports:` block on any datastore in the production file; asserted both by a `grep -c 'ports:'` count of exactly 1 and by a real `docker compose ps` assertion in Task 2. |
| T-06-33 | Spoofing | redis reporting healthy while unauthenticated, or never reporting healthy and masking a real outage | mitigate | The `environment: REDIS_PASSWORD` fix makes the authenticated healthcheck actually execute; `docker inspect … Health.Status == healthy` is asserted, not inferred from "container is running". |
| T-06-34 | Tampering | `api` serving traffic against an unmigrated schema | mitigate | `depends_on: migrate: condition: service_completed_successfully` plus `restart: "no"` on the one-shot; proven by the stack test reaching healthy only after `migrate` exits 0. |
| T-06-07 | Tampering | a restart silently changing version | mitigate | Every image reference interpolates `${NOODARA_VERSION}`; `:latest` is asserted absent by grep. |
| T-06-35 | Denial of Service | one container exhausting a 2 GB VPS's memory and taking the stack down | mitigate | `deploy.resources.limits.memory` on all six services, set from measured idle usage with 2× headroom. Residual risk under real load is explicitly carried into Plan 06-15's real-VPS validation rather than being declared closed here. |
| T-06-36 | Information Disclosure | a secret reaching a Compose `command:` array visible in `docker inspect`/`ps` output | accept | `redis-server --requirepass ${REDIS_PASSWORD}` puts the redis password on the container's command line, visible to anyone who can already run `docker inspect` on the host — i.e. root. This matches the dev file's existing shape and redis's own documented configuration surface; the alternative (a config file written by the installer) adds a second secret-bearing file on disk for no net gain against an attacker who already has root. Documented, not silently inherited. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new package. `postgres:17-alpine` and `redis:7-alpine` are the exact tags already in use in `docker-compose.dev.yml` since phase 1 — no new image source is introduced. |
</threat_model>
