<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container logs → installer stdout | `docker compose logs` output is surfaced to the operator on the failure path and mined for the setup token on the success path |
| installer → /opt/noodara/install.log | a persistent file on the host that an operator may later paste into a support request |
| installer → host firewall | the installer reads ufw state but is forbidden from changing it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-09 | Information Disclosure | secrets written to `install.log` | mitigate | `noodara_write_log` records step names and variable names only; a canary test runs the full flow and asserts no generated secret value and no token appears in the file. Log mode 600. |
| T-06-41 | Information Disclosure | the setup token leaking beyond the operator's terminal | mitigate | The token is read from the api logs and written only to stdout inside `noodara_print_summary`; it is never passed to `noodara_write_log`, never stored, and never re-emitted. Asserted by the same canary test. |
| T-06-42 | Information Disclosure | the D-12 diagnostic log tail dumping `.env` contents or an unredacted secret | mitigate | Only `docker compose logs --tail 50 <service>` is shown, and application logs already pass through the phase-1 pino redactor; a test asserts the failure path never prints `.env` contents. |
| T-06-05 | Information Disclosure | an operator believing ufw protects a Docker-published port when it does not | mitigate | D-08's advisory uses the precise "Docker publishes container ports by inserting its own iptables rules, which typically bypass ufw for published ports" wording; asserted by test and reused verbatim in `docs/install.md`. |
| T-06-43 | Tampering | the installer mutating firewall rules and opening the host further than the operator intended | mitigate | `noodara_check_ufw` is read-only; a test inspects the stub call log and fails if any mutating `ufw` subcommand is invoked. |
| T-06-44 | Denial of Service / data loss | a failed upgrade destroying data in an attempt to "recover" | mitigate | D-12: no automatic rollback and no destructive command on the failure path; asserted by a test that inspects the stub call log for `down`, `volume rm` and `.env` deletion. |
| T-06-45 | Spoofing | a fabricated or stale setup token printed when the api never emitted one | mitigate | `noodara_read_setup_token` returns non-zero when no line exists and the summary then prints the admin-exists message; the installer never generates a token itself (the token derivation lives in `bootstrap-admin.ts` and is HMAC-derived from the persisted row). |
| T-06-46 | Information Disclosure | HTTP-by-default panel traffic, including the session cookie, travelling unencrypted | accept-with-control | D-05 accepts HTTP for v0.1 (TLS is v0.4/Traefik). The controls are: an explicit warning in the summary, `NOODARA_COOKIE_INSECURE=true` written only in that case, and `docs/install.md` documenting the TLS-proxy path. The residual risk is accepted and stated to the operator rather than hidden. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new package. |
</threat_model>
