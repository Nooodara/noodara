<objective>
Create the release pipeline that produces the images `install.sh` pulls, and wire the installer
test suite into CI and nightly at the right cost point.

Purpose: D-01 makes the published GHCR images the only artifact a VPS ever fetches, so the release
workflow is part of the product's trust chain, not a convenience. D-16's arm64 support is only real
if the arm64 image is genuinely built and its native addons genuinely work. And the installer suite
is heavy enough (duration measured in Plan 06-12) that putting it on every pull request would push
the merge gate well past an hour.
Output: `release.yml`, plus targeted additions to `ci.yml` and `nightly.yml`.
</objective>

    `docker buildx imagetools create`. The `needs:` gate is exactly what closes Open Question 1's
    race concern; say so in a comment.

    unless both `linux/amd64` and `linux/arm64` appear. Without this step a silently single-arch
    release would only be discovered by an arm64 user's failed install.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → GHCR | the workflow holds a token that can publish the images every installation pulls |
| third-party actions → release pipeline | any unpinned action runs arbitrary code inside the job that signs and publishes releases |
| published manifest → every VPS | a wrong or incomplete manifest breaks every install on the missing architecture |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-54 | Tampering | a mutable action tag silently changing the code that builds and pushes release images | mitigate | Every third-party `uses:` pinned to a 40-character commit SHA with the tag as a trailing comment, the convention `ci.yml` already states and justifies. Any unresolvable SHA becomes an explicit TODO blocking Plan 06-15, never a floating tag. |
| T-06-55 | Elevation of Privilege | an over-scoped token on the release job | mitigate | Per-job `contents: read` plus `packages: write` only, using the built-in GITHUB_TOKEN. No PAT, no `id-token`, no `contents: write`. Asserted by grep. |
| T-06-25 | Spoofing | a published web image proxying `/api/*` somewhere other than the production api service | mitigate | The build arg is set to the literal `http://api:3000` in the workflow, matching the Compose service name; the wrong-origin negative control in Plan 06-05 proves a mismatch is detectable. |
| T-06-56 | Denial of Service | a release that is silently amd64-only, breaking every arm64 install | mitigate | The `verify` job runs `docker manifest inspect` and fails unless both platforms are present. Without it, D-16 would be an untested claim. |
| T-06-57 | Tampering | a partially published manifest left behind by a cancelled run | mitigate | `cancel-in-progress: false` on the release concurrency group, deliberately diverging from `ci.yml`, with the reason stated in a comment. |
| T-06-58 | Repudiation | a green local YAML file being mistaken for a passing gate | mitigate | The header comment states plainly that the workflow cannot fire without a remote (D-02), following `nightly.yml`'s existing precedent; Plan 06-15 carries the first real run as a human prerequisite. |
| T-06-59 | Denial of Service | doubling pull-request latency by adding the DinD suite to the merge gate | mitigate | The installer job is gated to push-on-main and nightly; the timeout is sized from the measured duration recorded in 06-12, not guessed; no existing job is modified. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new npm package. The `docker/*` GitHub Actions are recorded as Approved in 06-RESEARCH.md's Package Legitimacy Audit (first-party Docker Inc., verified publisher) with SHA pinning as the stated condition. |
</threat_model>
