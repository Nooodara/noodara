<objective>
Produce the second published image: `apps/web` as a Next.js standalone server, with the
Compose-internal API address baked in at build time, and prove the proxy actually works by curling
through a running web container into a running api container.

Purpose: 06-RESEARCH.md's second load-bearing finding is that Next.js evaluates `rewrites()` once
at `next build` and never again — so `NOODARA_API_ORIGIN` is a property of the published image tag,
not a runtime setting. The failure mode for a wrong-but-present value is not a crash but confusing
runtime 502s (Pitfall 3), which is why a build-succeeds check is insufficient and a real
proxied request is required.
Output: `output: 'standalone'` in `next.config.ts`, `apps/web/Dockerfile`, and an integration test
that proves the proxy end to end.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → web container | the only port published to the host; the sole public entry point in v0.1 |
| web container → api container | the same-origin proxy hop, inside the Compose network only |
| build-time env → published image | `NOODARA_API_ORIGIN` becomes an immutable property of every published tag |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-25 | Spoofing | a published `web` image proxying `/api/*` to a dev or attacker-chosen address | mitigate | `ARG NOODARA_API_ORIGIN` with no default makes an unset value a hard build failure (`readApiOrigin()` throws); the release workflow (Plan 06-13) is the only place the value is set, to the fixed Compose-internal `http://api:3000`. Proven by the wrong-origin negative control in Task 3. |
| T-06-26 | Elevation of Privilege | web container running as root | mitigate | Dedicated `nodejs` system user, `USER nodejs` before `CMD`, asserted by `docker run … id -u`. |
| T-06-27 | Tampering | clickjacking / referrer leakage regressions lost in the standalone build | mitigate | Task 3 asserts `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer` on a response served by the real standalone server, not by `next dev` — the phase-5 headers block is otherwise only exercised in dev/E2E. |
| T-06-28 | Information Disclosure | source maps or source tree shipped in the public image | accept | The Next.js standalone output ships client bundles as Next.js produces them; no additional source-map hardening is introduced in v0.1. Rationale: the web app is a client of an authenticated API and holds no secret; `apps/web` contains no credential handling. Revisit if a client-side secret is ever introduced. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new npm package; the image installs only from `pnpm-lock.yaml`. |
</threat_model>
