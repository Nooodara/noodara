    `connection-loss.test.ts` covers two scenarios:
    - **connection loss, after the fact**: connect successfully, stop the container, then `exec`. Assert the failure is `CONNECTION_LOST`. This ordering is deterministic by construction — the transport is provably gone before the command is issued.
    - **connection loss, mid-exec**: the branch that actually matters, because `error-classifier.ts` has a rule for a channel dying with a command in flight and nothing else in this phase drives it against real infrastructure. Stage it with plan 02-02's opt-in primitive, which keeps the production allowlist frozen: start `startSshd({ ubuntu, slowDf: true })` — an image whose only difference is that `/usr/local/bin/df` shadows `/usr/bin/df` with a shim that signals it started and then blocks — connect, call `session.exec('discovery.disk')` WITHOUT awaiting it, `await waitForSlowCommandStart(fixture)`, and only then `await fixture.stop()`. Finally await the exec promise and assert it resolved to a `CONNECTION_LOST` outcome matching ADR 0004's measured mid-exec row.
      Three things make this deterministic rather than a race, and the comment in the file must say so: the allowlisted command text is unchanged (`discovery.disk` is still `df -P -k /`; the shim is a property of the test image, not of the allowlist), the kill is sequenced after an *observed* marker rather than after a delay, and the shim blocks for ~20s so the kill lands with roughly nineteen seconds of margin. If the shim is somehow not in place the command returns real `df` output and the assertion fails loudly — it cannot hang and it cannot pass by accident.
      Run it under `describe.each` for both 22.04 and 24.04, and assert the outcome is a resolved value, never a rejection.
    - **reconnect**: start a fixture on a fixed host port, connect and close cleanly, then connect again and assert success with the same fingerprint and `fingerprintCaptured: false` when the fingerprint is pinned from the first connection. Then prove recovery after a transient failure: stop the container, attempt a connect (assert a failure outcome), start a fresh fixture on the same fixed host port, and assert a connect with no pinned fingerprint succeeds again — a server that failed once is not permanently unusable (PITFALLS.md #8).

    Every failure assertion must check that the promise resolved to an outcome. Add a process-level guard in each file: register an `unhandledRejection` listener in `beforeAll` that records anything it sees, and assert in `afterEach` that nothing was recorded. That is the only way these files actually prove SERV-07's "never crashes the API" rather than just "returns the right code".
