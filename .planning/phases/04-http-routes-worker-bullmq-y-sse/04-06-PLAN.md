```
export const QUEUE_NAME = 'servers';
export const CONNECT_SERVER_JOB_NAME = 'connect-server';
export const BULLMQ_PREFIX = 'noodara';
export function jobIdForServer(serverId: string): string;   // `connect:${serverId}`

export interface ConnectServerJobPayload {
  readonly serverId: string;
  readonly actor: { readonly type: 'user'; readonly id: string } | { readonly type: 'system' };
  readonly requestedAt: string;           // ISO-8601
  readonly trigger: 'connect' | 'discover';
}

export interface ConnectServerQueue {
  enqueue(payload: ConnectServerJobPayload):
    Promise<{ ok: true; jobId: string } | { ok: false; code: 'QUEUE_UNAVAILABLE'; message: string }>;
  isJobPending(serverId: string): Promise<boolean>;
  close(): Promise<void>;
}
export function createConnectServerQueue(options: { connection: Redis }): ConnectServerQueue;
```

Then create `apps/control-plane/src/queue/job-payload.ts`:
- `export const ConnectServerJobPayloadSchema` — a Zod 4 object with `serverId: z.uuid()`, `actor: z.discriminatedUnion('type', [z.object({ type: z.literal('user'), id: z.uuid() }).strict(), z.object({ type: z.literal('system') }).strict()])`, `requestedAt: z.iso.datetime()` (or the Zod 4 equivalent available in the pinned `zod@4.6.1` — check the installed types rather than guessing), `trigger: z.enum(['connect', 'discover'])`, and `.strict()` on the outer object.

- `export type ConnectServerJobPayload = z.infer<typeof ConnectServerJobPayloadSchema>` and assert at the type level that its `actor` member is assignable to `ServiceActor` (a `satisfies`/type-level check, so a drift in either type is a compile error).

Then create `apps/control-plane/src/redis/connections.ts` exporting two factories, each taking an explicit URL parameter (never reading `env` itself, so tests point them at the container):
- `createQueueRedisConnection(url: string): Redis` — `{ commandTimeout: 2000, maxRetriesPerRequest: 1, lazyConnect: false }`. The 2s bound is D-27's: this connection only ever issues short `queue.add`/`getJob` commands.
- `createWorkerRedisConnection(url: string): Redis` — `{ maxRetriesPerRequest: null }` and **no** `commandTimeout`. BullMQ requires the former, and a `commandTimeout` here would abort the worker's own long-blocking idle wait for new jobs. Put that reason in a comment directly above the option: these two settings are trivially swapped by mistake and the failure mode is subtle.
Both factories attach an `error` listener that logs at warn level and never rethrows, so an ioredis connection error can never surface as an unhandled rejection (D-27: no Redis failure escapes a handler).

Then create `apps/control-plane/src/queue/connect-server-queue.ts`:
- Export `QUEUE_NAME = 'servers'`, `CONNECT_SERVER_JOB_NAME = 'connect-server'`, `BULLMQ_PREFIX = 'noodara'` and `jobIdForServer(serverId) => \`connect:${serverId}\``. Every other module in the phase imports these constants rather than repeating a literal.
- `createConnectServerQueue({ connection })` constructs `new Queue(QUEUE_NAME, { connection, prefix: BULLMQ_PREFIX })` and returns the `ConnectServerQueue` port.
- `enqueue(payload)` calls `queue.add(CONNECT_SERVER_JOB_NAME, payload, { jobId: jobIdForServer(payload.serverId), attempts: 1, removeOnComplete: { count: 100 }, removeOnFail: { count: 500 } })`. `attempts: 1` is D-12: the SSH adapter already retries transients itself (Phase 2 D-10) and `connectAndDiscover` never throws for an SSH failure, so a BullMQ retry could only ever re-run a job whose failure was a real bug.
- Wrap the `add` in `Promise.race` against a 2000 ms timer and a `try/catch`; any rejection, or the timer winning, yields `{ ok: false, code: 'QUEUE_UNAVAILABLE', message: 'Job queue is unavailable' }`. The explicit race is belt-and-braces over ioredis's own `commandTimeout`, because a connection in mid-reconnect can sit in the offline queue instead of erroring. The message is a fixed string — never the ioredis error text, which can contain the Redis host and port.
- `isJobPending(serverId)` uses `queue.getJob(jobIdForServer(serverId))` and returns true when the job exists and is `waiting`, `active` or `delayed`; on any error it returns `false` (the worker's startup sweep treats "cannot tell" as "no live job", which is the safe direction: the sweep's action is itself idempotent).
- `close()` closes the `Queue` (not the connection — the caller owns the connection's lifetime).
- This module must not import `env.js`: the connection is injected, which is what lets the integration test point it at the Testcontainers Redis.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API process → Redis | Job data crosses a process boundary and is persisted outside Postgres' guarantees |
| Redis → worker process | Anything readable/writable in Redis is attacker-controlled if Redis is ever compromised or shared |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-03 | Tampering | `job.data` in Redis | mitigate | The payload schema is `.strict()` with a `discriminatedUnion` actor, and `parseConnectServerJobPayload` returns a result instead of throwing; the worker (Plan 04-07) validates on consume, so a tampered entry fails closed |
| T-4-26 | Information Disclosure | job payload contents | mitigate | The payload carries only `serverId`, `actor`, `requestedAt`, `trigger` — the worker re-reads the row and decrypts the credential itself, so no host, ssh user or credential ever sits in Redis (D-11) |
| T-4-08 | Denial of Service | Redis outage blocking the API | mitigate | `enqueue` is bounded by both ioredis `commandTimeout: 2000` and an explicit `Promise.race` timer, and converts every failure into `{ ok: false, code: 'QUEUE_UNAVAILABLE' }`; asserted against a genuinely stopped container |
| T-4-27 | Information Disclosure | queue error messages | mitigate | The `QUEUE_UNAVAILABLE` message is a fixed string; the ioredis error text (which embeds host/port) is never propagated into a result or a response body |
| T-4-28 | Tampering | key collisions in a shared Redis | mitigate | `prefix: 'noodara'` on the BullMQ queue and the same namespace for every other key this phase writes, asserted by a key scan |
</threat_model>
