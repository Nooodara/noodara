<objective>
Make the instance usable on a clean VPS and recoverable after a lost password or a rotated key, without email and without a manual database edit.

Three locked decisions land here. D-01 and D-04 decide how the very first admin comes to exist. D-03 makes password recovery a CLI command that reuses the setup-token machinery rather than inventing a second token system. D-11 makes master-key rotation a real operation — the counterweight to D-09's "lose the key and the credentials are gone".

Purpose: the phase-6 installer reads the setup token from `docker compose logs api`, so the boot output shape decided here is a contract that installer depends on.
Output: the boot bootstrap, the `noodara` CLI with two commands, and three integration suites.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Container stdout → operator / installer | The setup and recovery token values deliberately cross here; nothing else secret may |
| Operator shell (`docker compose exec`) → control plane | CLI commands run with full database access and both master keys in the environment |
| Old master key → new master key | Both are live in the process during rotation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-44 | Elevation of Privilege | Setup token re-printed on every boot | accept | D-01 requires it, and the exposure is bounded: printing stops the moment an admin exists, the token is single-use with a 24-hour TTL, and stdout is already an operator-only channel. Tests assert only the hash is persisted |
| T-1-45 | Elevation of Privilege | `noodara admin reset` as a backdoor | mitigate | Requires shell access to the container, issues a purpose-scoped single-use token rather than setting a password directly, checks `purpose` on redemption so a recovery token cannot create a second admin, and revokes every session on use (D-03) |
| T-1-46 | Spoofing | Session surviving a password reset | mitigate | Redemption revokes all sessions for the admin in the same transaction; asserted by a test |
| T-1-47 | Denial of Service (data loss) | Partially rotated credential table | mitigate | One transaction for the whole rotation, no catch-and-continue, target version computed once, already-rotated rows skipped so a retry is safe; the corrupt-row abort case is tested (D-11) |
| T-1-48 | Information Disclosure | CLI output during rotation | mitigate | Only row counts and key fingerprints are printed; a test asserts neither key, plaintext nor ciphertext appears in captured output (D-12) |
| T-1-49 | Elevation of Privilege | `NOODARA_ADMIN_PASSWORD` in the environment | mitigate | The pre-seed path validates the password against the domain policy and aborts the boot on failure; the value is redacted by the pino paths from Plan 01-03 and never written to an activity event |
</threat_model>
