<objective>
Close the supply-chain gate before a single dependency is installed in this greenfield repo.

`01-RESEARCH.md` ran `slopcheck --ecosystem npm` over the whole phase-1 dependency set. Three packages did not come back clean: `vitest` [SUS], `commander` [SUS] and `@fastify/type-provider-zod` (approved-with-caveat, Assumption A1). The research author assessed all three as false positives with independent, verifiable evidence — the objective signal in every case is the same one a human would read off the npm page: the package's registry `repository.url` field.

This plan turns that lookup into a script instead of a human gate. `scripts/check-package-provenance.mjs` asserts each pinned package resolves to its expected GitHub org, and fails the run with a review message on any mismatch. A typosquat cannot satisfy it, because a typosquat cannot claim the real org's repository and still be a different package.

Purpose: prevent a typosquat or hallucinated package from entering the lockfile of a security product on its first commit, and keep that check re-runnable on every dependency bump instead of expiring the moment the conversation ends.
Output: `scripts/check-package-provenance.mjs` and `docs/adr/0000-package-legitimacy-approvals.md` recording the verified provenance per package.
</objective>

  <action>
    Write `scripts/check-package-provenance.mjs` as a plain ES module executed with `node` and **zero third-party dependencies** — no `package.json` exists yet at this point in the phase and none may be created here.

    The script holds one hardcoded table mapping package name to expected GitHub `owner/repo`, per the research evidence:
    - `vitest` expects `vitest-dev/vitest`
    - `commander` expects `tj/commander.js`
    - `@fastify/type-provider-zod` expects `fastify/fastify-type-provider-zod`
    - `fastify-type-provider-zod` expects `turkerdev/fastify-type-provider-zod` (the unscoped alternative Plan 01-03 compares against; checked here so its provenance is on record too)

    For each entry, resolve the registry `repository.url`. Use `npm view <pkg> repository.url` through `node:child_process` `execFileSync` (npm is present on every machine that will run this repo, and it works with no local `package.json`). If `npm view` is unavailable or errors, fall back to `fetch('https://registry.npmjs.org/<encoded pkg>')` and read `repository.url` off the `latest` dist-tag's version object — Node 22 ships global `fetch`, so no dependency is needed either way. Also capture the resolved latest version string for the record.

    Normalise the returned URL before comparing: strip a leading `git+`, a trailing `.git`, `ssh://git@`/`git://`/`https://` prefixes and any `github.com[:/]` prefix, then lowercase. Compare the normalised `owner/repo` against the expected value with an exact string equality — do not use `includes`, which a URL like `github.com/evil/vitest-dev-vitest` would satisfy.

    On success the script prints one line per package with the package name, resolved version and observed repository, then exits 0. On any mismatch, unresolvable package or missing `repository` field it prints the offending package, the expected org, the observed value, and the literal sentence `SUPPLY CHAIN CHECK FAILED - a human must review this package on npmjs.com before it is installed`, then exits 1. Accumulate all failures and report them together rather than exiting on the first one.

    Then run the script and write `docs/adr/0000-package-legitimacy-approvals.md` from its real output. The ADR is a table whose columns are: Package, Expected repository, Observed repository, Resolved version, slopcheck verdict, Automated verdict, Date. Include one row for each of the four packages. Record the slopcheck verdicts from RESEARCH (`vitest` [SUS], `commander` [SUS], `@fastify/type-provider-zod` [OK]/A1, `fastify-type-provider-zod` [OK]) and the automated verdict as `verified` for each package the script accepted. Add the literal provenance line `Source: .planning/phases/01-dominio-persistencia-y-autenticaci-n/01-RESEARCH.md#package-legitimacy-audit` and a line stating that the check is re-runnable with `node scripts/check-package-provenance.mjs` and must be re-run whenever one of these pins changes.

    Do not run `pnpm install`, do not create a root `package.json` and do not create a lockfile in this plan — the whole point of this gate is that it precedes the first install. If the script exits non-zero for any package, stop: do not proceed to Plan 01-02, record the failing package and its observed repository in the SUMMARY, and surface it to the developer as a blocker requiring a replacement package.
