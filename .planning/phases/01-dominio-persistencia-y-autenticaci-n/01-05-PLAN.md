  <name>Task 2: AES-256-GCM envelope with per-row key version (SEC-01, D-10, D-11)</name>
  <files>packages/domain/src/security/envelope.ts, packages/domain/src/security/envelope.test.ts</files>
  <behavior>
    - `encryptSecret(plaintext, { key, version })` returns a string matching `^v\d+:[A-Za-z0-9+/=]+:[A-Za-z0-9+/=]+:[A-Za-z0-9+/=]+$` (D-10 format)
    - `decryptSecret(encryptSecret(p, k), keyMap)` returns exactly `p`, including for a 4 KB ed25519 private key body and for a plaintext containing multibyte UTF-8
    - Two encryptions of the same plaintext with the same key produce different nonces and different ciphertexts
    - The nonce decodes to exactly 12 bytes and the auth tag to exactly 16 bytes
    - Flipping one byte of the ciphertext segment makes `decryptSecret` throw `SecretTamperError`; flipping one byte of the tag segment does the same
    - Decrypting with a key that is not the encrypting key throws `SecretTamperError`, not a generic crypto error
    - Decrypting a blob whose version is absent from the key map throws `UnknownKeyVersionError` naming the version
    - `keyMap` accepts multiple versions at once: a blob written at v1 and a blob written at v2 both decrypt in the same call sequence (D-11 rotation window)
    - `encryptSecret` rejects a key whose length is not 32 bytes with `InvalidKeyLengthError`
    - `decryptSecret` rejects a malformed blob (wrong segment count, non-numeric version, non-base64 segment) with `MalformedBlobError` and never with a stack trace containing ciphertext
    - `reencryptSecret(blob, keyMap, targetKey)` decrypts under the old version and re-encrypts under the new one, returning a blob whose version equals the target version (the primitive `noodara secrets rotate` uses in Plan 01-14)
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application memory → PostgreSQL rows | Plaintext credentials must not cross this boundary |
| Application memory → logs / errors / activity log / API responses | Every one of these is a user- or operator-visible surface |
| Old master key → new master key (rotation window) | Both keys are live simultaneously during `noodara secrets rotate` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-09 | Information Disclosure | `SecretValue` serialisation | mitigate | `toString`, `toJSON` and the node inspect symbol all return `[REDACTED:<kind>]`; tests assert `JSON.stringify` and `util.inspect` never emit the raw value (skill section 1) |
| T-1-10 | Tampering | Encrypted credential rows | mitigate | AES-256-GCM authenticated encryption; a modified ciphertext or tag raises `SecretTamperError` on decrypt, verified by two dedicated tests (SEC-01) |
| T-1-11 | Information Disclosure | Error messages from the crypto layer | mitigate | `SecretTamperError` and `MalformedBlobError` carry no plaintext, ciphertext or key material; asserted by test |
| T-1-12 | Denial of Service (data loss) | Master key loss / rotation | mitigate | Per-blob `v<version>` prefix plus a version→key map makes old rows readable during rotation; `reencryptSecret` exists from day one (D-10, D-11; Coolify APP_KEY "MAC invalid" pattern) |
</threat_model>
