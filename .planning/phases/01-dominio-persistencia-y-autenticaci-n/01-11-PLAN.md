<objective>
Resolve RESEARCH Open Question 1 with a concrete, tested mechanism, and deliver the session model and endpoints D-06 asks for.

D-05 (as clarified on 2026-09-10) says: sesión de 7 días deslizante con tope absoluto de 30 días desde el login, donde "deslizante" significa que la actividad renueva la expiración con una cadencia máxima de una renovación por día, para no escribir en la base de datos en cada request. That maps directly onto Better Auth: `expiresIn` is the 7-day sliding window and `updateAge` is 1 day, so a request inside the same day is a no-op for `expires_at` while a request after a day or more pushes it out another 7 days. An `absolute_expires_at` column set at session creation clamps every subsequent refresh — so `expires_at` can never exceed `absolute_expires_at`, and the 30-day ceiling is enforced by ordinary expiry rather than by a bespoke validation path. A session used a diario nunca caduca antes del tope de 30 días.

Purpose: closing the open question with a test rather than a reading of the docs. D-06's endpoints land here too; only their Settings UI is deferred to phase 5.
Output: `session-policy.ts`, a session application service, three routes, and two integration suites.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `/api/sessions*` | Authenticated but attacker-reachable if a cookie is stolen; the revocation endpoints are the containment tool |
| Session row → API response | Session tokens live in the same row as the metadata being displayed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-30 | Spoofing | Long-lived stolen session cookie | mitigate | 7-day sliding window renewed at most once per day, plus a structural 30-day ceiling via `absolute_expires_at` clamping, so a stolen cookie has a bounded life even with attacker-driven activity (D-05); `DELETE /api/sessions` gives the admin immediate containment (D-06) |
| T-1-31 | Information Disclosure | Session listing response | mitigate | Explicit Zod output schema with no token field, asserted by a test that stringifies the whole response body and searches for each real token (noodara-security section 5) |
| T-1-32 | Information Disclosure | Revocation of a non-owned session id | mitigate | Returns 404 rather than 403, so the endpoint does not confirm the existence of sessions the caller does not own |
| T-1-33 | Repudiation | Untracked session revocation | mitigate | Every revocation writes `auth.session_revoked` through the single activity writer, inside the revocation transaction |
</threat_model>
