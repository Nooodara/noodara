<objective>
Build the single write path into `activity_events` and prove, with canary values, that it cannot carry a secret.

AUTH-04 requires failed logins in the activity log "sin incluir el password". The domain type from Plan 01-06 already refuses to construct an event whose metadata contains a forbidden key; this plan adds the second layer — the Redactor pass — and the integration proof.

Purpose: Plan 01-12 (setup), Plan 01-13 (lockout) and every phase-3 service call this one function. ARCHITECTURE section 6 is explicit that routes and workers never write events directly, and the only way to make that true is for there to be exactly one writer.
Output: `writeActivityEvent`, the `toLogSafe` mapper, and two integration suites.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application code → `activity_events` rows | These rows are rendered to the admin in phase 5, making the table a more direct leak vector than application logs |
| Application code → pino stdout | Readable via `docker compose logs` by anyone with host access |
| Application code → HTTP error responses | Reachable by an unauthenticated client on the setup and login routes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-22 | Information Disclosure | `activity_events.metadata` | mitigate | Two independent layers: `buildActivityEvent` rejects forbidden keys and `SecretValue` instances outright, and `writeActivityEvent` runs the Redactor over metadata before insert; both asserted, plus a canary proof that fails when the redact call is removed (AUTH-04, PITFALLS.md #2) |
| T-1-23 | Information Disclosure | Unhandled error bodies on public routes | mitigate | The canary test drives a thrown error through the Fastify error handler and asserts the canary is absent from the response body, covering the "credenciales nunca expuestas en API responses" acceptance item of roadmap section 6.3 |
| T-1-24 | Repudiation | Missing or partial auth audit trail | mitigate | The writer participates in the caller's transaction, so an event either lands with its state change or neither does; a rollback test asserts this |
</threat_model>
