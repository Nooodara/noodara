cascade of `"sse broadcaster subscriber redis error"` (`AggregateError`) culminating in `"sse

`tests/integration/activity/auth-events.test.ts`, essentially the start of the suite, and failures
continue through the end). This is the documented "Docker hiccup … cascades into hundreds of

### Section 1b — `pnpm test:e2e`: 1 real (non-flaky, non-environmental) failure

`92 passed (1.4m)`, `1 failed`:

```
1) [chromium] › tests/e2e/host-key.spec.ts:429:1 › @hostkey UF-01 regression: editing the host
   while ERROR/HOST_KEY_CHANGED clears the pending fingerprint, so the trust affordance disappears
   and the trusted fingerprint stays unchanged
   Error: expect(received).toBe(expected)
   Expected: "ssh-ed25519 SHA256:0YT++OJbqfolUdiU6O1+suTXfkYNzkxDX0Nkb3F8I9U"
   Received: null
   at tests/e2e/host-key.spec.ts:504:43
```

**Classification: a real, deterministic consequence of this round's own intentional GR-02 fix — not
a regression bug, not a flake, not environmental.** This test (added by plan 05-19, commit
`1dddd11`, predates round 2 and is not in 05-40's `files_modified`) edits only `host` while the
server is `ERROR`/`HOST_KEY_CHANGED`, then asserts `afterEditBody.hostFingerprint === originalFingerprint`
(line 504) — i.e. it encodes the *pre*-GR-02 expectation that a host-identity edit clears only
`pendingFingerprint`, leaving the trusted `hostFingerprint` untouched. Plan 05-40 (this round)
deliberately changed that: `edit-server.ts`'s `hostIdentityChanged` block (confirmed by direct read,
line 264-266: `if (hostIdentityChanged) { statusPatch = { ...statusPatch, hostFingerprint: null,
hostFingerprintCapturedAt: null }; }`) now clears `hostFingerprint` unconditionally whenever `host`
or `sshPort` changes, from **any** status — this is 05-40's own documented `must_haves.truths`:
"Re-pointing a server at a different host or port clears the old host's trusted fingerprint from ANY
status, so the next connect is a clean TOFU first capture instead of a guaranteed spurious
HOST_KEY_CHANGED." That is exactly what this E2E test does (edits `host` to
`renamed-....example.test`) and exactly the behavior GR-02 intentionally changed. The test's own
code comment ("The trusted fingerprint is untouched — only the *pending* one was ever at risk…")
states the pre-fix mental model 05-40 superseded on purpose.

**Not classified as a documented flake:** `deferred-items.md`'s two named flakes are both in
`tests/e2e/servers-list.spec.ts` (the `row.hover()` timeout and the keyboard-activation SSE case) —
an unrelated file and an unrelated, bimodal-timeout failure shape. This failure is a deterministic
`toBe` value mismatch with a fully-explained root cause from source reading, not a timing race, so
no `deferred-items.md` citation applies and none is claimed.

**Not fixed here, per this plan's own hard rule.** `tests/e2e/host-key.spec.ts` was not edited.
Flagged as a residual for a follow-up plan: update this test's final two assertions to expect
`hostFingerprint === null` (matching GR-02's now-intended behavior) instead of the pre-fix value,
with its own RED/GREEN cycle. This is a real, if narrow, process gap in 05-40's own scope (it audited
and added new integration coverage for GR-02 but did not audit pre-existing E2E coverage for
assertions the fix would invalidate).
