Build the activity log screen (ACT-02): day-grouped sentences, curated expandable detail, cursor pagination and event-driven refresh.

Purpose: ACT-02 requires a readable audit trail whose metadata never contains sensitive values. The API already redacts at write time; D-14 adds a second, client-side allowlist so a future backend field cannot appear in the UI by accident. "Only keys the UI knows" has to be structural, not a habit.
Output: the screen, two tested pure modules, and E2E coverage of the states, the pagination and the drop-unknown-keys rule.
</objective>

<interfaces>
`GET /api/activity?limit=50&cursor=<opaque>` → `{ items: ActivityItem[], nextCursor: string | null }` where `ActivityItem` is `{ id, occurredAt, actorType: 'user' | 'system', actorId: string | null, entityType, entityId: string | null, action, outcome: 'success' | 'failure', errorCode: string | null, metadata: unknown }`. The querystring is `.strict()`: an unrecognised parameter is a 400, so no filter may be added. `limit` is 1–200.

The fourteen actions come from `packages/domain/src/activity` — eight `auth.*` plus six `server.*`.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `activity_events.metadata` (jsonb) → rendered DOM | The one place arbitrary stored structure could reach a page |
| a future backend metadata field → the UI | A field added server-side must not appear without a UI decision |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-64 | Information Disclosure | metadata rendering | mitigate | Client-side per-action key allowlist (`curatedDetailFor`), unexpected value types dropped, zero `JSON.stringify`; a component test asserts an unknown key reaches no part of the rendered row and the E2E asserts the same at page level — defence in depth over the server's write-time redaction (SEC-02) |
| T-5-65 | Tampering | XSS via a metadata string | mitigate | React escaping; the repo-wide no-raw-HTML grep gate (Plan 05-21) covers these components |
| T-5-66 | Information Disclosure | actor identity exposure | accept | Single-admin model: "Admin"/"System" plus the email already stored in metadata is the intended audit content, and the API's ten-column projection is the enforcing boundary |
| T-5-67 | Tampering | cursor manipulation | transfer | The cursor is opaque and validated server-side (`decodeActivityCursor`); the client passes it back verbatim and never constructs one |
| T-5-68 | Denial of Service | unbounded page growth from repeated Load older | accept | Explicit user action per 50 rows, no infinite scroll — the interaction itself is the bound |
| T-5-SC | Tampering | npm installs | mitigate | No new packages in this plan |
</threat_model>
