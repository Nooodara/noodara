**IMPORTANT — 05-REVIEW.md GR-02's literal fix text is over-broad and must not be followed verbatim.** It says to clear `hostFingerprint` "in the `identityChanged` block", but `identityChanged` includes `sshUser`. Clearing the trusted host key on an SSH-user-only change would reset TOFU for a host that already has a trust relationship — a security REGRESSION (the next connect would silently accept whatever key is presented, including an interceptor's). It also directly contradicts an existing, deliberate test: `tests/integration/services/edit-server.test.ts` at ~line 417, "CONNECTED + ssh user change only transitions to DISCONNECTED and preserves the fingerprint (D-14 access)", which asserts `row?.hostFingerprint).not.toBeNull()` at ~line 424.

The correct scope is a NEW predicate for host identity only: `host !== row.host || sshPort !== row.sshPort`. That matches `classifyServerEdit`'s own `'identity'` semantics and keeps the existing D-14 test green.

Next-connect behaviour with a null `hostFingerprint`: `connect-and-discover.ts` (~line 306) computes `trustedFingerprint` from the row, and `packages/ssh/src/ssh2-adapter.ts` treats `trustedFingerprint === null` as a first capture (`fingerprintCaptured: true`, no `HOST_KEY_CHANGED`). So a cleared fingerprint means the next connect re-establishes TOFU against the new host — the intended behaviour for a row that was just re-pointed at a machine it never had a trust relationship with. This must be asserted, not assumed.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin's edit of `host`/`sshPort` → which machine the row's trusted key belongs to | An identity edit silently re-points a trust relationship at a machine that never had one |
| `hostFingerprint` present vs null → `trustedFingerprint` passed to `ssh.connect` | Null means "first capture, accept and record"; non-null means "verify or fail closed" |

| T-5G-40-01 | Spoofing | alarm fatigue from a spurious `HOST_KEY_CHANGED` after every non-CONNECTED re-point | mitigate | Clear `hostFingerprint`/`hostFingerprintCapturedAt` whenever `host` or `sshPort` changes, from any status, so the warning only ever fires for a real mismatch on the same target |
