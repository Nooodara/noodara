<objective>
Close 05-REVIEW.md GR-03: in `connectAndDiscover`'s catch block, `await failInFlightConnection(deps, {...}).catch(() => undefined)` deliberately preserves and rethrows the original error (correct), but if the recovery call itself throws — a transient Postgres error while trying to un-wedge the row — that failure is discarded with zero log output. CLAUDE.md §2.2 requires explicit handling and adequate logs for every infrastructure failure path. The worker's `'failed'` listener provides a second, logged recovery attempt, so recovery is not lost — but if the second attempt succeeds, nobody is ever told the first one failed, hiding a real signal (a flaky database) behind an apparently clean recovery.

Purpose: an invisible failure on a recovery path is the kind of thing that turns a one-line DB warning into a week-long mystery.

Output: an optional `logger` on `ServerServicesDeps`, one small unit-tested helper that logs the swallowed failure without leaking anything, and its wiring into the existing catch — with the rethrow semantics untouched.
</objective>
