## Tokens

Single source of truth: `.claude/skills/noodara-ux-apple/SKILL.md` §2 (color, typography, spacing, radii, elevation, motion). Do not redeclare or reinterpret values here beyond what implementation requires.

- **`packages/ui/tokens.css`**: every token in skill §2.1–§2.3 as CSS custom properties, scoped under `:root` (light values) and `[data-theme="dark"]` (dark values). Dark is visually primary but light must not be `prefers-color-scheme`-only — both selectors are explicit so a manual override always wins over the media query.
- **Tailwind preset**: Tailwind v4 (CSS-first `@theme` block) — the natural fit for "tokens as CSS custom properties, never hex inline," since v4 lets `@theme` reference `var(--token)` directly instead of duplicating values into a JS config. Exact Tailwind version is pinned by the planner/executor through the ADR-0000 provenance gate in Wave 1, matching how `typescript-eslint`, `bullmq`, etc. were pinned in prior phases — not decided here. `packages/ui` exports the Tailwind config/`@theme` import; `apps/web` consumes it, never redefines colors locally.
- **Theme switching**: `data-theme="dark" | "light"` attribute on `<html>`, driven by (1) `prefers-color-scheme` on first load with no stored preference, (2) a manual toggle persisted to `localStorage` (`noodara-theme`) that overrides the media query from then on. No-flash requirement: the root layout (`apps/web/src/app/layout.tsx`, a Server Component) inlines a tiny blocking `<script>` before any stylesheet/hydration that reads `localStorage.getItem('noodara-theme')`, falls back to `matchMedia('(prefers-color-scheme: dark)')`, and sets `data-theme` synchronously — the same pattern `next-themes` uses internally, hand-rolled here to avoid a new dependency for ~15 lines of code. `ThemeToggle` (packages/ui) is the only component that ever writes `localStorage`/`data-theme` after load.
- **Never**: hex/rgb/px-literal-font-size inline in any `apps/web` or `packages/ui` component — always a `--token` or a Tailwind class backed by one.

## Spacing Scale

The skill's actual scale (not the generic template default) — **8px base, with 4 and 12 reserved for typographic micro-adjustments only**:

| Token | Value | Usage |
|-------|-------|-------|
| space-1 | 4px | icon-to-label gaps, tight inline adjustments |
| space-2 | 8px | compact control spacing (badge padding, chip gaps) |
| space-3 | 12px | typographic micro-adjustment only, never a layout gap |
| space-4 | 16px | default control/element spacing, input padding |
| space-5 | 20px | card padding |
| space-6 | 24px | section-internal spacing |
| space-8 | 32px | section padding, sheet content padding, page content padding |
| space-12 | 48px | major section breaks (settings groups) |

Exceptions:
- Touch targets ≥ 44px on any tappable control (row height, mobile nav items) even where the base grid would suggest less — skill §3.
- Desktop table/list rows: 44px height; desktop form controls: 32–36px height (buttons 32px, inputs 36px) — not on the 8px grid, explicitly called out by the skill as fixed control heights, not spacing.
- Radii and motion durations are separate scales (see below), not spacing.

Radii: `--r-sm` 6px (controls, inputs, chips), `--r-md` 10px (cards, selected rows, popovers), `--r-lg` 16px (sheets, modal panels), `--r-pill` 9999px (status pills, primary toolbar button).

## Typography

The skill defines **eight semantic type roles**, not a generic 3–4-size scale — this supersedes the template's default because the project skill is the locked source of truth (per this agent's own instructions: "Its values are LOCKED; do not invent a different palette, scale or font stack"). Every phase-5 screen must draw only from this table; no ad hoc sizes.

| Role | Size / Weight / Line-height / Tracking | Usage in this phase |
|------|------|--------|-------------|
| `--text-display` | 28px / 600 / 1.14 / -0.02em | Page title: server name on detail page, "Servers", "Activity", "Settings" |
| `--text-title` | 20px / 600 / 1.2 / -0.015em | Section titles: "Discovery", sheet titles, settings group headers |
| `--text-headline` | 15px / 600 / 1.33 / -0.01em | List row primary text (server name), stat tile labels' parent row |
| `--text-body` | 15px / 400 / 1.47 / -0.01em | Default body copy: empty-state sentences, form help text, dialog body |
| `--text-callout` | 13px / 400 / 1.38 / 0 | Table/list cell text, sidebar items, activity sentences |
| `--text-caption` | 12px / 400 / 1.33 / 0 | Metadata, timestamps, status pill labels, stat tile deltas |
| `--text-label` | 11px / 600 / 1.2 / 0.04em uppercase | Section eyebrows, table headers, sidebar group headers |
| `--text-mono` | 13px / 400 / 1.5 / 0 | `host:port`, fingerprints, error codes, discovery `detail`/`durationMs`, activity metadata values, config values |

## Color

The skill's tokens already encode the 60/30/10 split structurally — `--canvas` is the dominant surface, `--surface-1/2/3` are the secondary surface family, `--accent` is the one 10% action color. Semantic status tokens are a separate, non-decorative axis reserved exclusively for infrastructure state.

| Role | Token(s) | Usage |
|------|-------|-------|
| Dominant (60%) | `--canvas` (dark `#161618` / light `#f5f5f7`) | App background behind sidebar/content |
| Secondary (30%) | `--surface-1` (`#1d1d1f` / `#ffffff`), `--surface-2` (`#252527` / `#fafafc`), `--surface-3` (`#2a2a2c` / `#f0f0f2`) | Sidebar, toolbar, cards, sheets, inputs, popovers, table row hover |
| Accent (10%) | `--accent` (`#2997ff` / `#0071e3`), `--accent-soft` | See explicit reserved-for list below |
| Destructive | `--status-error` (`#ff453a` / `#ff3b30`) | Destructive actions only (delete, trust-new-fingerprint confirm) |

**Accent (`--accent`/`--accent-soft`/`--on-accent`) is reserved for exactly:**
- Primary button fill + `--on-accent` text: "Save and connect", "Connect", "Re-run discovery", "Save", setup/login submit
- Text links: server name link inside an activity row, "Back to Servers" link on the detail page
- Focus ring on any focusable element (`outline: 2px solid var(--accent)`)
- Checked/selected state of Radix-based controls: segmented control's selected option, checkbox/radio checked fill
- Active sidebar nav item background (`--accent-soft`) and its text (`--ink`)
- Selected table row background (`--accent-soft`) — not used in this phase's flat server list (no multi-select), reserved for future use

**Never** used for: status pills (those are semantic, never accent), ghost/secondary button text, destructive actions, decorative emphasis of any kind.

Semantic status tokens (never decoration, only `ServerStatus`/`DiscoveryCheckStatus`-derived state):

| Token | Dark / Light | Maps to |
|---|---|---|
| `--status-ok` | `#30d158` / `#34c759` | `ServerStatus.CONNECTED`, discovery check/step "pass" |
| `--status-warn` | `#ff9f0a` / `#ff9500` | `ServerStatus.CONNECTING`, discovery check/step "warning" (see §Discovery below) |
| `--status-error` | `#ff453a` / `#ff3b30` | `ServerStatus.ERROR`, `ServerStatus.UNREACHABLE`, discovery check/step "fail", destructive actions |
| `--status-idle` | `#8e8e93` (both modes) | `ServerStatus.PENDING`, `ServerStatus.DISCONNECTED`, discovery check/step "not applicable"/"skipped"/"pending" |

⚠️ **Accessibility finding — flag for the skill owner, not silently fixed here** (see full detail under Accessibility below): computed contrast shows every status pill's full-saturation text on its own `-soft` background token **fails WCAG AA in light mode** (measured ≈2.0–3.1:1 against the required 4.5:1 for 12px pill text), while the identical pairing in dark mode passes comfortably (≈6.1–6.3:1). This is a token-level gap in the locked skill, not something this UI-SPEC can fix by inventing a new color — raised as an open question for the user/skill owner.

## 1. Shell (UI-01)

Three-pane macOS model from skill §3, with the inspector unused in v0.1 (D-10) — effectively a two-pane shell (sidebar + content, toolbar sticky inside content).

```
≥1280px:  [Sidebar 240px, translucent] [Toolbar 52px sticky | Content, max-width 1120px, padding 32px]
900–1279: [Sidebar 64px, icons only]   [Toolbar | Content]
<900:     [Content full width]          Bottom sheet nav triggered by a toolbar menu button
```

**Sidebar** — exactly three entity items, no v0.2+ placeholders (CLAUDE.md §8, D-Discretion):
1. Servers (icon: `Server`)
2. Activity (icon: `History`)
3. Settings (icon: `Settings`)

Grouped under a `--text-label` eyebrow is unnecessary for three flat items — render as a plain list, `--text-callout` 500 weight, `--r-sm` active-state background `--accent-soft`. Below the nav list, separated by a hairline, a bottom cluster holds:
- `ThemeToggle` (icon button, sun/moon, cycles light → dark → system)
- "Sign out" (ghost button, available from this fixed position on every authenticated screen, satisfying AUTH-03's "desde cualquier pantalla")

**Toolbar**: view title left (`--text-title`), at most one primary action right (per screen — see per-screen table below), secondary actions ghost. On server detail, the toolbar also carries a small "← Servers" ghost link, left of the title.

**Keyboard navigation & focus order** (skill §7, "navegación completa por teclado"):
1. Skip-to-content link (visually hidden until focused) — first tab stop
2. Sidebar items, top to bottom (Servers → Activity → Settings)
3. Theme toggle → Sign out
4. Toolbar back-link (if present) → toolbar title (not focusable) → toolbar primary action → toolbar secondary actions
5. Content, in DOM/visual order (table rows via row-level `⋯` menu button, form fields top to bottom)
6. Pagination/"Load older" control, if present, at the end of content

Focus is always visible (`outline: 2px solid var(--accent); outline-offset: 2px`, per skill §4.1) — no `outline: none` anywhere without a replacement focus style.

**Responsive breakpoints** (skill §3, verbatim):
- ≥1280px: sidebar expanded (240px, labels visible)
- 900–1279px: sidebar collapses to a 64px icon rail (tooltips on hover/focus show the label)
- <900px: sidebar becomes a bottom sheet, triggered by a hamburger-style menu button that replaces the toolbar's back-link slot on server detail; content is a single column

### 2.1 Setup (`/setup`)

Task: redeem the one-time setup token and create the single admin account (AUTH-01). No sidebar/shell — full-viewport centered card, `--surface-1`, `--r-lg`, 400px wide, matching the skill's "sheet" surface treatment even outside a sheet context since there is no authenticated shell yet.

Fields: Token (pre-filled from the URL query string if present, e.g. `/setup?token=...`, else empty, mono input), Email, Password (with the same 12–128-char policy as AUTH-02, shown as help text under the field, never a strength meter). Submit: "Create admin account".

- **Loading**: skeleton for the three fields while nothing async happens client-side (this screen has no pre-check API call to load) — effectively instant; this state is mostly relevant for the button's own inline spinner-less loading (Button `loading` state = label unchanged, disabled, subtle opacity per skill).
- **Error** (mirrors 01-CONTEXT.md's semantics, never revealed as a distinct case to the user beyond the message itself):
  - Token missing/invalid/expired/already used → banner: "This setup link is no longer valid. Ask whoever installed Noodara for a new one." (API's `NOT_FOUND`/400 from `POST /api/setup` never distinguishes "already has an admin" 404 from a bad token in the copy — same message either way, since 05-CONTEXT.md's discretion note says follow phase-1's semantics of never revealing which condition applies)
  - Validation failure (weak password, invalid email) → inline field errors from `issues[].path`
- On success: redirect to `/login` with a neutral toast "Admin account created. Sign in to continue."

### 2.2 Login (`/login`)

Task: authenticate the single admin (AUTH-02). Same centered-card treatment as setup, no shell.

Fields: Email, Password. Submit: "Sign in". No "forgot password" link in v0.1 (recovery is CLI-only per phase 1; not adding a UI entry point this phase — out of scope, `/api/recovery` has no UI consumer).

- **Loading**: submit button `loading` state (disabled, label unchanged, no spinner per skill's "spinners a pantalla completa" ban — a subtle opacity/scale-down on the button itself is enough, matching the 120ms press micro-interaction).
- **Error**:
  - Invalid credentials → inline banner under the form: "That email or password isn't right." — **never** "no account with that email" or any phrasing that reveals whether the email exists (AUTH-04, discretion note "sin revelar si una cuenta existe").
  - Lockout (429 `TOO_MANY_REQUESTS` from Better Auth, `LOGIN_LOCKED`) → same banner slot: "Too many attempts. Try again in {retryAfter}." — read `Retry-After` header, render as a relative duration ("in 2 minutes"), not a raw seconds count.
- On success: redirect to `/servers` (or the originally-requested protected URL if the user was redirected here by a 401).

### 2.3 Servers list (`/servers`) — SERV-04

Task: see every registered server at a glance and act on one. Toolbar: title "Servers", primary "Add server" (opens the create sheet).

List: hairline rows, 44px, per D-09 — Name (`--text-headline`) · `host:port` (`--text-mono`, `--text-callout` size) · StatusPill · last seen (relative, `--text-caption`, ISO tooltip). Row click navigates to `/servers/:id`. Row-level `⋯` menu (visible on hover/focus, not a permanent column, per skill §4.4): "Edit", "Delete". No cards, no alternate layout for few servers (D-09, deferred idea explicitly rejected).

- **Empty**: title "No servers yet" (`--text-title`), body "Connect your first Ubuntu server to let Noodara discover it." (`--ink-secondary`), single button "Add server" (primary). No illustration.
- **Loading**: 5 skeleton rows, exact 44px geometry, `--surface-2` blocks for name/host/pill/timestamp — never a spinner.
- **Error**: hairline banner, `--status-error-soft` background, "Couldn't load servers. {message}" + `error_code` in mono + "Retry" ghost button.

### 2.4 Add/edit server sheet — SERV-01, SERV-02

Task: register a new server or edit an existing one. Right-side sheet, 480px, `--r-lg`, translucent `--surface-1`, over the current view (list or detail) — never a separate page.

Fields, in order:
1. Name (text input)
2. Host (text input, help text: "Hostname or IP address")
3. SSH port (number input, default 22, placeholder shown not pre-filled-as-value so it stays genuinely optional)
4. SSH user (text input, default `root`, same placeholder treatment)
5. Credential — **SegmentedControl**: "Private key" (default/selected) / "Password" (D-04)
   - Private key selected: mono `Textarea` for the key (placeholder "Paste your private key, or choose a file"), "Choose file" ghost button beside it that reads the file client-side (`FileReader.readAsText`) and fills the textarea — never a multipart upload, the file's text becomes the same JSON field the pasted-key path uses. Optional Passphrase input below (type="password"-equivalent masked text). Help text: "ed25519 keys are recommended."
   - Password selected: single masked text input.
   - **Edit mode**: this whole block collapses to a single row — `••••••••` (mono, `--ink-tertiary`) + "Replace" ghost button; clicking "Replace" expands the same create-mode fields in place, credential is never pre-filled.

Buttons: primary **"Save and connect"** (create only, D-01) triggers register → `POST /connect` → close sheet → navigate to `/servers/:id`; secondary ghost "Save without connecting" (create only) registers and stays on the list; edit mode has a single primary "Save" (no auto-connect — editing an already-CONNECTED server must not implicitly reconnect it). Cancel: ghost, closes the sheet, discards all field state including any loaded key text.

- **Validation**: inline, per field, sourced from `VALIDATION_FAILED`'s `issues[].path` (e.g. `sshPort` → "Port must be between 1 and 65535" under the SSH port field). `NAME_TAKEN` → error under Name: `A server named "{name}" already exists.`; `HOST_TAKEN` → error under Host: `A server at {host}:{port} is already registered.` `INVALID_CREDENTIAL` → error under the credential block: "This credential could not be parsed. Check the key format (or password) and try again."
- **Loading**: primary button `loading` state; fields disabled while the request is in flight.
- **Error** (non-field, e.g. `SERVER_BUSY` on edit): toast, sheet stays open with the user's input intact.
- Focus trap + `Esc`-to-close (Radix Dialog/Sheet primitive), first field auto-focused on open.

### 2.5 Server detail (`/servers/:id`) — DETL-01, DETL-02, DISC-02

Own page, own URL (D-10). Toolbar: "← Servers" link, page title = server name (`--text-display`) + StatusPill inline, primary action mutually exclusive by status:

| Server status | Toolbar primary |
|---|---|
| PENDING | "Connect" |
| CONNECTING | "Connect" (disabled, see Real-time behavior) |
| CONNECTED | "Re-run discovery" |
| UNREACHABLE / ERROR (not `HOST_KEY_CHANGED`) | "Retry" (re-runs connect) |
| ERROR with `lastErrorCode === 'HOST_KEY_CHANGED'` | none in the toolbar — the action lives in the error banner itself ("Trust new fingerprint"), since it needs the type-the-name dialog, not a bare click |

**Layout, top to bottom** (D-11):
1. First-trust notice (D-02) — dismissible, one-time, only shown once per server the first time `hostFingerprintCapturedAt` is set and the user hasn't dismissed it (persisted client-side, e.g. `localStorage` keyed by server id — dismissal is cosmetic only, the fingerprint row below is permanent regardless)
2. `HOST_KEY_CHANGED` error banner (D-03), when applicable — replaces the generic error banner for this one code
3. Generic error banner (DETL-02 "discovery failed" case), when applicable and not `HOST_KEY_CHANGED`
4. Stat tile row: CPU cores · RAM · Disk (used/total + 1px meter) · Uptime — all mono, tabular numerals, each labeled "as of {last discovery relative time}"
5. Label/value groups: **System** (hostname, OS, architecture), **Docker** (engine version, compose version), **Connection** (host, port, user, credential type, fingerprint + captured-at date + copy button, last seen)
6. **Discovery** section (see §5 below)

**Empty — never discovered** (DETL-02): stat tiles and label/value groups collapse to a single empty-state block: title "Not discovered yet." (no separate heading needed, one line is enough per the skill's empty-state minimalism), button "Connect". No banner above it (nothing has failed yet).

**Error — discovery failed** (DETL-02): banner on top (position 2/3 above), redacted by `lastErrorCode` (Copy Deck below), `error_code` in mono at the banner's end, one action button (Copy Deck: "Retry" or "Trust new fingerprint"). **Facts from the last good discovery stay visible below the banner, visually dimmed** (`opacity: 0.6` or `--ink-tertiary` for values) with their own "as of" date — the backend never overwrites a known value with `null` (mergeDiscoveryFacts), so this is a true rendering rule, not a fallback. If there has never been a good discovery, the banner sits directly above the "Not discovered yet" empty block instead of above real data.

- **Loading**: skeleton stat tiles (4 blocks, same geometry as the real tiles) + skeleton label/value rows, shown only on the very first load of the page (not on every SSE-driven update — those patch in place, no re-skeletonizing already-visible data).

### 2.6 Activity log (`/activity`) — ACT-02

Task: chronological audit trail. No shell primary action (nothing to create here).

Rows grouped under day headers (`--text-label`, e.g. "TODAY", "YESTERDAY", "SEP 17"). Each row: one sentence (D-14, Copy Deck below) + relative time (ISO tooltip) + `error_code` in mono for failures only. Expand chevron reveals a small label/value block of curated keys (Copy Deck below) — rows whose action has no known metadata keys show no chevron at all rather than an empty expanded panel.

Pagination: ghost "Load older" button at the bottom, D-13 — first 50 rows on load, click appends the next 50 using the opaque `nextCursor`. No infinite scroll, no filters/search (Out of Scope table).

- **Empty**: "No activity yet" / "Actions you take will show up here."
- **Loading**: 10 skeleton rows under one skeleton day-header block.
- **Error**: banner "Couldn't load activity. {message}" + `error_code` mono + "Retry".
- **Refresh** (discretion): no dedicated SSE event this phase — refetch page 1 (a) when the tab regains focus (`visibilitychange`), (b) whenever any `server.updated`/`server.deleted` SSE event arrives while this page is open, since those almost always correspond to a fresh activity row. This does not reset scroll position or already-loaded older pages; it only re-fetches and merges page 1, matching the cursor's "opaque, forward-only" contract.

### 2.7 Settings (`/settings`) — SET-01

No sidebar primary action. Two groups, both read-only (D-16):

**Instance** (always expanded): version (`--text-mono`), public URL (`--text-mono`, with a copy button).

**Advanced** (collapsed by default, Disclosure component): master key fingerprint (mono, 16 hex chars, e.g. `a1b2c3d4e5f6a7b8`), SSH timeouts (connect/command/discovery, each in seconds, mono), worker concurrency (mono integer). - **Empty**: not applicable (config always exists once the app boots).

## 4. Discovery Checklist Component (DISC-02, D-05..D-08)

### 4.1 Structure

Six named steps, in fixed order, mapped from connection result + the eleven `DiscoveryCheckId`s (D-06):

| Step | Source | Checks (order fixed by `DISCOVERY_CHECK_IDS`) |
|---|---|---|
| SSH reachable | connection result, not a discovery check | fails on `HOST_UNRESOLVED` / `CONNECT_TIMEOUT` / `CONNECTION_LOST` |
| Authenticated | connection result, not a discovery check | fails on `AUTH_FAILED` / `HOST_KEY_CHANGED` (host identity is verified as part of establishing a trusted, authenticated session — **researcher decision**, not spelled out in 02/05-CONTEXT.md; flagged as an open question below) |
| OS | `hostname`, `os_release`, `arch` | |
| Resources | `cpu`, `memory`, `disk`, `uptime` | |
| Docker | `docker_version`, `docker_compose_version` | |
| Access | `sudo`, `docker_group` | |

A step passes only if every check in it passes (D-06). Expanding a step reveals its raw checks, each with `id`, status token+icon+label, `detail` and `durationMs` in mono.

### 4.2 Per-check severity (color) mapping — researcher decision

The domain only reports four `DiscoveryCheckStatus` values (`pass`/`fail`/`skipped`/`not_applicable`); D-08's three-color rule ("warning for a failure that leaves the server usable, red only for the check that ended the run") requires a UI-side classification this contract makes explicit:

| Domain status | Check id | UI severity | Token |
|---|---|---|---|
| `pass` | any except `os_release` with `warnings` containing `UNSUPPORTED_OS` | pass | `--status-ok` |
| `pass` | `os_release`, and `warnings` includes `UNSUPPORTED_OS` | warning | `--status-warn` |
| `fail` | `docker_version`, `docker_compose_version`, `sudo`, `docker_group` | warning | `--status-warn` |
| `fail` | any other id (`hostname`, `os_release`, `arch`, `cpu`, `memory`, `disk`, `uptime`) | fail | `--status-error` |
| `skipped` | any | idle | `--status-idle` |
| `not_applicable` | any | idle | `--status-idle` |
| (not yet run) | any | pending | `--status-idle`, label "Pending" |
| (next check in sequence, run in progress) | any | running | `--status-warn` dot with the pill's pulse animation (skill §4.2), label "Running" |

State is never color-only: every check/step renders its status word (Pass / Warning / Fail / Not applicable / Skipped / Pending / Running) next to the dot/icon, plus a distinct icon per severity (check / triangle / x / minus / clock) — `aria-label` on the icon duplicates the same word for screen readers.

Step (group) aggregation: `fail` if any check in it is a true fail; else `warning` if any check in it is a warning; else `pass` if every check passed; else `idle` if every check is skipped/not_applicable (e.g. Access when connected as root).

### 4.3 Live vs. settled

- **Live** (server status `CONNECTING`): both connection-derived steps (SSH reachable, Authenticated) render `running` from the moment the toolbar shows "Connecting…"; the four discovery-group steps render `pending`. As each `server.discovery_progress` event (§7 below) arrives, the first arrival implicitly resolves both connection steps to `pass` (discovery only starts after a successful, authenticated connection) and resolves that specific check within its group; the next unresolved check in `DISCOVERY_CHECK_IDS` order shows `running`. The section stays expanded during a live run.
- **Settled** (server status anything but `CONNECTING`): the section collapses to a one-line summary — `"Discovered {relative time}, {passedSteps} of {applicableSteps} passed{, {warningSteps} warning(s)}{, {failedSteps} failed}"` — clicking it expands the full six-step checklist. `applicableSteps` excludes steps that are entirely `idle`/not-applicable (e.g. Access for a root connection); `passedSteps`/`warningSteps`/`failedSteps` are mutually exclusive step-level counts. (05-CONTEXT.md's own example phrasing, "6 of 6 passed, 1 warning," is illustrative copy, not a literal count formula — this algorithm is the researcher's concrete resolution, flagged below as open for the user to confirm.)
- **Page opened mid-run** (D-05's "never invent progress"): on load, fetch the read endpoint (§7) for the **last completed run's** settled checklist, but do **not** render it as if it were current — if `server.status === 'CONNECTING'`, render all six steps as `pending`/`running` per the live rule above, discarding the fetched settled data entirely until the run currently in flight produces its own events and finally settles. A small caption under the section header reads "A new discovery run is in progress" while in this state so the user understands why the checklist reset.
- **"Re-run discovery" only affects the last run** (D-07: "Solo el último run tiene UI en v0.1") — no history of prior runs is shown or fetchable in this phase (Deferred Ideas).
- **`prefers-reduced-motion`**: the `running` pulse becomes a static (non-animated) `--status-warn` dot; no other motion in this component beyond that pulse.

## 6. Real-Time Behavior

- **Status pill transitions**: 200ms crossfade between two pill states on any `server.updated` SSE event touching the viewed/listed server (skill §2.4) — no rebound, no rebuild-from-scratch re-render of the row.
- **Stream-dropped indicator**: a small, subtle inline indicator (e.g. a dot + "Reconnecting…" in `--ink-tertiary`, `--text-caption`) appears near the toolbar whenever the browser's native `EventSource` fires an `error`/closes; it disappears the moment a new connection opens and the app has refetched. **Never** presents stale data as live during this window — any status pill or stat tile currently on screen keeps its last-known value but the reconnecting indicator makes clear it may be out of date.
- **Resync on reconnect**: no event replay (D-01..D-07 locked). On `EventSource.onopen` after a prior drop, refetch `GET /api/servers` (list view) or `GET /api/servers/:id` + the discovery read endpoint (detail view) to resynchronize, exactly like a normal page load.
- **401 on the stream or any fetch**: immediate redirect to `/login` (fase 4 D-01/D-05/D-06 — the heartbeat's own session re-validation already closes the stream server-side on an invalid session; the client only needs to react to the resulting `close`/subsequent fetch 401).
- **Connect button while a connect is in flight**: disabled the instant the local optimistic state or an incoming `server.updated` shows `CONNECTING`; a `409 ALREADY_CONNECTING` response to a stray click is swallowed as a no-op state confirmation, never surfaced as an error toast (discretion note, matches D-08's "el rojo solo aparece cuando algo está realmente roto").
- **"As of" labelling**: every discovered fact (stat tiles, System/Docker/Connection label-value groups) carries "as of {relative time}" derived from the server's `lastSeenAt` (or the specific discovery snapshot's `collectedAt` once the read endpoint is wired) — never presented as a live-updating metric. Relative timestamps everywhere use a tooltip with the full ISO string on hover/focus.

### 7.1 SSE event: `server.discovery_progress`

## 8. Accessibility

- **Contrast — verified by computation, not assumption**:
  - `--ink-secondary` on `--surface-1`: dark ≈ **6.5:1** (PASS AA), light ≈ **5.1:1** (PASS AA, tightest margin in the system — do not further desaturate `--ink-secondary` in light mode).
  - `--on-accent` (white) on `--accent`: light ≈ **4.7:1** (PASS AA, narrow margin), dark comfortably higher (lighter blue on dark background).
  - ⚠️ **Status pill text on its own `-soft` background**: dark mode passes comfortably (`--status-ok` ≈6.1:1, `--status-warn` ≈6.3:1). **Light mode fails AA for pill-sized (12px) text across every semantic color measured** — `--status-ok` ≈2.0:1, `--status-warn` ≈2.0:1, `--status-error` ≈3.1:1, `--status-idle` ≈2.8:1 — all well under the 4.5:1 small-text threshold. This is a systemic property of "full-saturation text on a 10–14%-alpha chip over a near-white surface," not a one-off mistake, and it is not something this UI-SPEC can fix by inventing a new token (the skill's tokens are locked). **Flagged as an open question for the user/skill owner below** — likely fixes are either a higher soft-background alpha in light mode specifically, or a separate, darker `--status-*-on-soft` text token for light mode; either requires a skill change, not an ad hoc component-level override.
  - Every other token pairing used by this phase (banner text on `--status-error-soft`, mono text on `--canvas`/`--surface-2`) must still be spot-checked with a contrast tool during implementation and re-verified by `noodara-ux-review` before sign-off — the two findings above are the ones with computed evidence in hand now.
- **State never color-only**: status pills always render their text label; discovery check/step icons always carry `aria-label` matching the visible word (Pass/Warning/Fail/Not applicable/Skipped/Pending/Running).
- **Focus**: visible 2px accent outline everywhere (skill §4.1); Sheet and Dialog trap focus and close on `Esc` (Radix's built-in behavior, do not override it).
- **ARIA / live regions**: the discovery section's live-updating list is `aria-live="polite"` (not `assertive` — per-check updates should not interrupt a screen reader mid-sentence) and updates are throttled to one announcement per settled check, never per intermediate render; the stream-dropped indicator is also `aria-live="polite"`.
- **Touch targets**: ≥44px on any tappable control at any breakpoint, including the collapsed 64px sidebar's icon buttons and the `⋯` row menu trigger.
- **`prefers-reduced-motion`**: crossfades and the discovery pulse degrade to instant/opacity-only transitions; nothing in this phase animates continuously besides the discovery `running` pulse and the SSE connection's own reconnect indicator (both already gated by this preference).
- **`prefers-color-scheme`** honored on first load with no stored override (see Tokens above).

## 10. Security-Relevant UI Rules (feeds QA-05)

- Credential fields (private key textarea, passphrase, password) are **never pre-filled** on edit — the sheet shows `••••••••` + "Replace" and only renders a real input once "Replace" is clicked, starting from an empty value.
- Credential values are **never** written to `console.*`, never included in a URL (query string or path), and never persisted to `localStorage`/`sessionStorage`/any client cache beyond the in-memory form state of the single mutation in flight — clearing on sheet close/unmount.
- The private-key file path reads the file with `FileReader.readAsText()` entirely in the browser and writes the result into the same textarea state the paste path uses; the request body is always the JSON shape `WireCredentialSchema` already defines (`{ type: 'ssh_private_key', privateKey, passphrase? }` or `{ type: 'ssh_password', password }`) — **never** a `multipart/form-data` upload.
- No screen ever renders a stored credential's value back — `ServerView`/`ServerViewSchema` structurally cannot carry one (SEC-02, `credentialType` only), so there is nothing to accidentally render; this is a backend guarantee the UI inherits rather than something the UI itself has to enforce.
- Autofill: credential inputs get `autoComplete="off"` (private key/passphrase/ssh password) to discourage the browser's password manager from offering to save an SSH credential as if it were a website login; the login form's own email/password fields keep normal `autoComplete="username"/"current-password"` since that is a legitimate login form.
- Any client-side error boundary/toast that surfaces a caught exception must pass it through the same "never echo raw input" discipline as the backend — render `error.message` from the API's own `{ error, message }` body, never `JSON.stringify` of a request payload or a raw `Error.stack`.
