Close the UI half of VERIFICATION gap 6 (05-REVIEW.md WR-B-12, and item 3 of `.planning/todos/pending/2026-09-19-trust-fingerprint-toctou.md`), on top of the backend binding plan 05-27 ships.

Re-verified on 2026-09-20: `apps/web/src/components/TrustFingerprintDialog.tsx`'s `handleConfirm` re-fetches the server and compares `latest.data.pendingFingerprint !== server.pendingFingerprint` — where `server` is the LIVE prop threaded down from `servers/[id]/page.tsx`'s SSE-updated state, not a snapshot of what the dialog rendered when it opened. A `server.updated` event arriving while the admin reads the fingerprint silently updates the prop, so the re-GET compares the new value against the new value and passes. The file's own header comment documents the residual race honestly and says a tighter guarantee "would need the route to accept and verify the exact fingerprint being trusted" — plan 05-27 makes that route change; this plan consumes it.

Purpose: this dialog is the one surface in Noodara that can hand a real SSH credential to an impostor host. Display and action must be structurally coupled, the same way `DeleteServerDialog`'s `confirmName` couples them.
Output: a snapshot-on-open dialog that sends the fingerprint it showed, correct copy for the new failure codes, and the mid-review-swap regression E2E.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| what the admin saw → what the backend promotes | The entire point of this plan; the coupling is the control |
| SSE `server.updated` → the dialog's rendered fingerprint | A live prop update is the attacker-observable swap channel |
| backend error codes → rendered copy | Codes cross into user-facing text |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5G-31-01 | Spoofing | mid-review fingerprint swap trusted by accident | mitigate | Snapshot on `open` + send that exact value; backend's atomic conditional promote rejects anything else with 409. E2E proves the swap is rejected. |
| T-5G-31-02 | Spoofing | a 409 degrading to `INTERNAL_ERROR` and the admin retrying blindly | mitigate | Both new codes added to the union AND the runtime allowlist, with a drift test |
| T-5G-31-03 | Elevation of Privilege | a stale typed confirmation name carrying into a second attempt | mitigate | The mismatch branch closes the dialog so `DestructiveConfirmDialog` resets `requiredName`; asserted in the component test |
| T-5G-31-04 | Information Disclosure | fingerprint or credential in logs / error copy | mitigate | Fingerprints are public (D-16) and displayed by design; copy contains no value interpolation and no `console.*` is added. Credentials never touch this component. |
| T-5G-31-05 | Repudiation | a promotion with no record of which value was trusted | mitigate | The backend's `server.fingerprint_trusted` activity event already records `previousFingerprint`/`newFingerprint` (verified in 05-27); confirm it still fires on the happy path |
| T-5G-31-06 | Tampering | removing the client re-GET weakening the guard | accept | The re-GET was never a control (it compared the live prop to itself); backend enforcement strictly supersedes it. Documented in the rewritten header comment. |
| T-5-31-SC | Tampering | npm/pnpm installs | mitigate | NO new dependency. If one seems necessary, stop and report. |
</threat_model>
