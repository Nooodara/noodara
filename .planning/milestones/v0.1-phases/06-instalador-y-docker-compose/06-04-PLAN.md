<objective>
Implement the `.env` half of INST-01/INST-02: generate a complete, per-installation set of secrets
on a fresh install, and on a re-run append only genuinely missing keys while leaving every existing
value byte-identical.

Purpose: Dokploy shipped CVE-2026-24840 by baking a fallback database password into its installer
(PITFALLS #1). Noodara's differentiator is that every installation's secrets are unique and that
the control plane refuses to boot on a weak one (INST-06, already implemented). This plan makes the
installer's generated values provably acceptable to that existing validator — including the
non-obvious constraint that a base64 secret cannot be embedded in `DATABASE_URL`/`REDIS_URL`.
Output: the env functions in `install.sh`, `.env.example`'s missing `NOODARA_COOKIE_INSECURE` entry,
a shell unit suite and an integration test that feeds a generated `.env` to the real validator.
</objective>

Binding constraint discovered by reading `apps/control-plane/src/env.ts` directly:
`NOODARA_MASTER_KEY` must be valid base64 decoding to exactly 32 bytes, so
`openssl rand -base64 32` is correct for it and only it. Every other generated secret ends up
either inside a URL (`DATABASE_URL`, `REDIS_URL`) or inside a Compose-interpolated `.env` value,
where base64's `/`, `+` and `=` corrupt URL parsing. Use `openssl rand -hex 32` for those.

`.claude/skills/noodara-security/SKILL.md` §8 applies to shell output exactly as it does to pino.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| install.sh → /opt/noodara/.env | the only place live production secrets are written on the host |
| install.sh → operator terminal / install.log | anything printed here may end up in a shared terminal scrollback, a screenshot or a support ticket |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-03 | Elevation of Privilege | a hardcoded or fallback database password (Dokploy CVE-2026-24840 precedent) | mitigate | Every secret comes from `openssl rand` per installation; `install.sh` contains no literal secret. Proven by the "two fresh generations differ for every secret key" test and by `env.ts`'s existing `WEAK_DB_PASSWORDS`/`WEAK_SECRETS` denylists as an independent second layer. |
| T-06-04 | Information Disclosure | `.env` and `.env.bak-*` file mode/ownership | mitigate | `umask 077` before the first write, explicit `chmod 600` after, `noodara_secure_env_file` re-asserted on every run including backups. Mode asserted in tests. |
| T-06-02 | Information Disclosure | generated secrets reaching stdout/stderr/install.log | mitigate | A canary-style test captures both streams during generation and asserts none of the generated values appears. Output helpers name variables only. |
| T-06-11 | Tampering | a re-run clobbering existing secrets and orphaning the encrypted credential rows | mitigate | `noodara_env_append_if_missing` never rewrites an existing line; the merge path is proven to change exactly one line; a timestamped mode-600 backup precedes every mutation. Losing `NOODARA_MASTER_KEY` makes every stored SSH credential unrecoverable, which is why this is a mitigate, not an accept. |

| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new package. `openssl` is a preflight-checked base command (Plan 06-02), not an install. |
