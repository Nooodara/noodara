Build the first production Docker image this repository has ever produced: one control-plane image
that serves as `api`, `worker`, the one-shot `migrate` job and the `noodara` operator CLI, plus the

`dist/config-version.js`'s `createRequire('../package.json')` resolves in a stripped runner stage —
so the plan verifies all three for real instead of trusting RESEARCH.md.
Output: `apps/control-plane/Dockerfile`, `.dockerignore`, and an integration test that builds the
image and exercises all four entrypoints.
</objective>

    Write `apps/control-plane/Dockerfile` with a header comment stating that this one image is
    `api`, `worker`, the one-shot `migrate` service and the `noodara` CLI (phase 4 D-23 / ADR 0003:
    one image, several `command:` overrides), and that the build context is the repo root.

    Base image `node:22-slim` for every stage (matches `engines.node: ">=22.12.0"` and `.nvmrc`;
    debian-slim over alpine per 06-RESEARCH.md's native-addon headroom rationale). Pin the base to
    a digest is NOT required for v0.1, but pin the tag exactly as `node:22-slim`.

    Stages:
    1. `pruner` — `corepack enable`, `WORKDIR /app`, `COPY . .`, then a deterministic prune. Do not
       use a bare `npx turbo` (it resolves an unpinned version from the registry at build time,
       which contradicts this repo's provenance posture). Instead run
       `pnpm install --frozen-lockfile --ignore-scripts` followed by
       `pnpm exec turbo prune @noodara/control-plane --docker`, so the turbo binary comes from the
       locked tree. If Task 1's spike showed that install to be prohibitively slow, the fallback is
       `pnpm dlx turbo@<the exact version in package.json> prune …` — record which one you used and why.
    2. `installer` — `corepack enable`, `COPY --from=pruner /app/out/json/ .`,
       `COPY --from=pruner /app/out/pnpm-lock.yaml ./pnpm-lock.yaml`, plus an explicit
       `COPY --from=pruner /app/out/json/pnpm-workspace.yaml ./` only if Task 1 found it is not
       already inside `out/json/`. Then `pnpm install --frozen-lockfile` (scripts enabled, so
       argon2's native binding is built or its prebuild fetched).
    3. `builder` — `COPY --from=installer /app/ .`, `COPY --from=pruner /app/out/full/ .`, then
       `pnpm exec turbo run build --filter=@noodara/control-plane`. This runs
       `tsc -p tsconfig.build.json && node scripts/copy-migration-assets.mjs` plus `^build` for
       `@noodara/domain` and `@noodara/ssh`.
    4. `runner` — `WORKDIR /app`, create a dedicated system user
       (`groupadd --system noodara && useradd --system --gid noodara --home-dir /app noodara`),
       then `COPY --from=builder --chown=noodara:noodara /app /app`. Copying the whole pruned
       workspace is deliberate: pnpm's isolated `node_modules` is a symlink tree rooted at
       `/app/node_modules/.pnpm`, so copying only `apps/control-plane/dist` would leave every
       workspace and dependency symlink dangling. Document that reason in a comment so a future
       size optimisation does not silently break module resolution.
       Then `WORKDIR /app/apps/control-plane`, `ENV NODE_ENV=production`, `USER noodara`,
       `EXPOSE 3000`, `CMD ["node", "dist/server.js"]`.

    Do not add a `HEALTHCHECK` instruction here — the healthcheck lives in the production Compose
    file (Plan 06-07) so `api`, `worker` and `migrate` can share one image with different health
    semantics.

    Add an `ARG NOODARA_IMAGE_VERSION` in the `builder` stage and, immediately before the build
    step, run `node -e` (or `pnpm pkg set version=…`) to stamp
    `apps/control-plane/package.json`'s `version` field with it when the arg is non-empty. This is
    what makes `GET /health` and `GET /api/config` report the released tag instead of the
    placeholder `0.0.0` (`apps/control-plane/src/config-version.ts` reads that field at runtime).
    When the arg is empty the version stays whatever the repo has, so local builds keep working.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer workstation → Docker build context | whatever is not in `.dockerignore` is copied into an image layer that will be published publicly |
| published image → every VPS | the image is executed as the control plane on every installation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-18 | Information Disclosure | build context leaking a real `.env` | mitigate | `.dockerignore` excludes `.env` and `.env.*` with no negation, verified by an automated grep in Task 1's acceptance criteria. A published layer containing live secrets is unrecoverable once pushed. |
| T-06-19 | Elevation of Privilege | container running as root | mitigate | Dedicated `noodara` system user created in the runner stage; `USER noodara` before `CMD`; asserted by `docker run … id -u` returning non-zero. |
| T-06-20 | Tampering | unpinned build-time tooling (`npx turbo@latest`) resolving arbitrary code at image-build time | mitigate | The pruner stage installs turbo from `pnpm-lock.yaml` (`pnpm install --frozen-lockfile` then `pnpm exec turbo`); a bare `npx turbo` is explicitly banned by Task 2's acceptance criteria. |
| T-06-21 | Spoofing | `/health` and `/api/config` reporting a version that is not the released tag | mitigate | `NOODARA_IMAGE_VERSION` build arg stamps `apps/control-plane/package.json`'s `version` before the build; proven by the `9.9.9-test` assertion. Without it every release would report `0.0.0` and an operator could not tell which version is running. |
| T-06-22 | Information Disclosure | test output echoing the fake secrets used to boot the container | mitigate | The test never prints its env map; failures assert on named fields only (noodara-security §8). Fake values reuse the shapes already present in `vitest.config.ts`. |
| T-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new npm package. `pnpm install --frozen-lockfile` inside the image installs only what `pnpm-lock.yaml` already pins; `apt-get` is not used at all (the `node:22-slim` base already provides everything needed). |
</threat_model>
