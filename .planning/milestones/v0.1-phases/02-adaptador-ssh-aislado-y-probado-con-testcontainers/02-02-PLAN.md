    `sshd-ubuntu-22.04/Dockerfile` and `sshd-ubuntu-24.04/Dockerfile` are identical except for the `FROM` line (`ubuntu:22.04` / `ubuntu:24.04`). Each one:
    - Declares `ARG WITH_DOCKER_CLI=false` and `ARG WITH_SLOW_DF=false`.
    - Installs `openssh-server`, `sudo` and `ca-certificates` with `apt-get install -y --no-install-recommends` and cleans `/var/lib/apt/lists` in the same layer.
    - When `WITH_DOCKER_CLI` is `true`, additionally installs the Docker CLI and the compose plugin **without any daemon**. Prefer Ubuntu's own `docker.io` package if it can be installed without pulling `containerd`/`dockerd`; if it cannot, install `docker-ce-cli` and `docker-compose-plugin` from Docker's apt repository. The daemon must never run inside this container — the point of the variant is a present CLI with an unreachable daemon (D-12, and the shape plan 02-04's spike B measures). Implement the conditional as a single `RUN` with an `if [ "$WITH_DOCKER_CLI" = "true" ]` guard, so both variants share the earlier layers.
    - Creates `/keys` and generates the user keypairs at build time with `ssh-keygen -q -N ''`: `ed25519` (type ed25519), `rsa3072` (`-t rsa -b 3072`), `ecdsa` (`-t ecdsa -b 256`), and `ed25519_unauthorized` (an ed25519 key deliberately installed in no `authorized_keys` file, for the AUTH_FAILED scenario). Keys are generated during `docker build` and therefore never enter git.
    - When `WITH_SLOW_DF` is `true`, copies `sshd-common/slow-df.sh` to `/usr/local/bin/df` with mode 0755. On Ubuntu `/usr/local/bin` precedes `/usr/bin` in the default non-login `PATH`, so an unmodified `df -P -k /` — the frozen `discovery.disk` template, which this plan does not and must not change — resolves to the shim. The production allowlist stays frozen; only the test image's `df` binary differs, and only when the build arg is set. Default `false` means every other scenario, and every image the other plans build, is byte-identical to today's.
    - Runs `sshd-common/setup-users.sh` at build time.
    - Copies `sshd-common/sshd_config.d/noodara-test.conf` into `/etc/ssh/sshd_config.d/`.
    - `EXPOSE 22`, `ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]`.

    `setup-users.sh` (build time) creates exactly four principals and documents each one's purpose in a comment:
    - `root` — `authorized_keys` gets the `ed25519`, `rsa3072` and `ecdsa` public keys. `PermitRootLogin prohibit-password`.
    - `deployer` — non-root, member of a `docker` group the script creates (the group must exist even though no daemon does — `id -nG` membership is what SERV-08 checks), and a `/etc/sudoers.d/deployer` entry granting `ALL=(ALL) NOPASSWD:ALL` installed with mode 0440. `authorized_keys` gets the same three public keys.
    - `restricted` — non-root, NOT in `docker`, NO sudoers entry. Same three public keys. This is the user that must produce `status: fail` on both SERV-08 checks.
    - `pwuser` — non-root, password authentication only, no `authorized_keys` at all. Its password is NOT set here (see the entrypoint).
    Each user gets `/home/<user>/.ssh` at 0700 and `authorized_keys` at 0600 owned by the user.

    `slow-df.sh` (`set -eu`, only present when `WITH_SLOW_DF=true`): `touch /tmp/noodara-slow-df-started`, then `sleep 20`, then `exec /usr/bin/df "$@"`. Two properties make it a scenario primitive rather than a sleep: the marker file is an *observable* signal that the command is now blocked inside the channel (the test waits on the marker, never on a clock), and the final `exec` means that if nothing kills the connection the command still returns real `df` output and exits 0 — a forgotten scenario degrades into a slow pass, never a hang. Write nothing to stdout or stderr before the sleep: the point of the scenario is a channel that has produced no output yet when the transport dies.

    `noodara-test.conf`: `PubkeyAuthentication yes`, `PasswordAuthentication yes`, `KbdInteractiveAuthentication yes`, `UsePAM yes`, `PermitRootLogin prohibit-password`, `LoginGraceTime 30`, `MaxStartups 20`, `LogLevel VERBOSE`. `KbdInteractiveAuthentication yes` is required by D-03 — the adapter tries `password` and `keyboard-interactive` with the same password, and the fixture must actually offer both methods.

    `entrypoint.sh` (container start, `set -eu`):
    - `rm -f /etc/ssh/ssh_host_*` then `ssh-keygen -A`. Fresh host keys on every start is what makes the HOST_KEY_CHANGED scenario deterministic: two containers from the same image present different host keys with no in-place sshd restart and no image rebuild.
    - If `SSH_TEST_PASSWORD` is set in the environment, `chpasswd` it onto `pwuser`; if it is not set, lock `pwuser`'s password. The helper supplies a per-run random value, so no password is committed and gitleaks needs no allowlist entry for these files.
    - If `SSH_TEST_KEY_PASSPHRASE` is set, generate `/keys/ed25519_locked` with `ssh-keygen -q -t ed25519 -N "$SSH_TEST_KEY_PASSPHRASE" -f /keys/ed25519_locked`, and append its public key to root's and `deployer`'s `authorized_keys`. This is D-02's passphrase-protected key fixture, again with no committed secret.
    - `mkdir -p /run/sshd` and `exec /usr/sbin/sshd -D -e` last, so sshd's startup log goes to the container's stdout where a Testcontainers wait strategy can match it.

    `startBlackholeListener()` — a container that accepts TCP on a port and then sends nothing, ever. Implement it as a minimal image or a `GenericContainer('alpine:3.21')` with a command that holds the socket open without writing (for example a `nc -lk` loop, or a `socat` sink); label it `noodara.test=true`, expose the port, wait on a log line or a port-listening strategy. It returns `{ host, port, stop }`. A TCP peer that accepts but never sends a version banner makes `ssh2`'s `readyTimeout` the only possible outcome, which is deterministic on macOS Docker Desktop and on GitHub `ubuntu-latest` alike — unlike the unroutable `10.255.255.1` address 02-RESEARCH.md flags as assumption A4. Plan 02-04's spike C measures both and records the decision; build this one now because it is the candidate most likely to win.

    `waitForSlowCommandStart(fixture)` — the observable trigger for the mid-exec connection-loss scenario (plan 02-10). Use no timer and no `setTimeout` between attempts: each `container.exec` round trip is itself the pacing, which is what keeps this an observed precondition rather than a fixed delay. Document in a comment that a caller who has awaited this function *knows* the remote `df` is blocked inside its sleep with output still pending, so a subsequent `stop()` lands mid-exec deterministically with roughly 19 seconds of margin — the difference between this and racing a kill against a timer.

    `assertNoStrayTestContainers()` — the extracted form of the assertion currently inlined in `migrations.test.ts`: list containers via `getContainerRuntimeClient()` and assert none carries `noodara.test=true`.
