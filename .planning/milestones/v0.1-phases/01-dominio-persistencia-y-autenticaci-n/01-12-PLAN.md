<objective>
Implement AUTH-01: the only way a Noodara instance gets its admin is by redeeming a valid, single-use, 24-hour setup token, and after that the door is gone.

Purpose: this is the highest-value target in the product. Whoever redeems the token owns the control plane and, through it, every registered server. The two failure modes that matter are a token that can be replayed and a race where two simultaneous requests both succeed — this plan tests both explicitly.

Same token model serves the `noodara admin reset` recovery flow (D-03); Plan 01-14 issues recovery tokens through the exact functions built here.
Output: the pure token module, the redemption service, the setup route, the sign-up gate, and two integration suites.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Unauthenticated internet → `POST /api/setup` | Before the admin exists this endpoint hands out total control of the instance |
| Unauthenticated internet → `POST /api/auth/sign-up/email` | Better Auth's generic sign-up route would otherwise be a second, ungated path to an account |
| Token value in stdout → operator | The token travels through `docker compose logs api` (D-01) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-34 | Elevation of Privilege | Setup-token race ("first visitor becomes admin") | mitigate | `pg_advisory_xact_lock` on a fixed key serialises redemption, the admin-existence re-check happens inside the lock, and the token row is taken `FOR UPDATE`; proven by a 10-way concurrent test asserting exactly one user row |
| T-1-35 | Elevation of Privilege | Token replay | mitigate | `used_at` is set in the same transaction as user creation, `isTokenUsable` rejects used and expired tokens, and the 24-hour TTL bounds the window (AUTH-01, D-02) |
| T-1-36 | Elevation of Privilege | Ungated Better Auth sign-up route | mitigate | `signupGate` returns 404 for `/sign-up/email` unless the AsyncLocalStorage bootstrap flag is active, so the only route to an account is the token-gated one |
| T-1-37 | Information Disclosure | Setup error responses and activity metadata | mitigate | Error bodies never echo the token or password; the `auth.setup_completed` metadata is asserted free of both; token comparison is constant-time on the hash |
| T-1-38 | Spoofing | Token guessing | mitigate | At least 32 bytes of `randomBytes` entropy, stored only as a SHA-256 hash, compared with `timingSafeEqual` |
</threat_model>
