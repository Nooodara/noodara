<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin-supplied host/user/name → future SSH command templates | Values validated here end up near a remote shell in phase 2 |
| Admin-supplied password → argon2id hashing | Weak or reused credentials are the whole attack surface of a single-admin control plane |
| Application code → activity_events rows shown in the UI | The activity log is read by a human and is a direct leak vector |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-13 | Tampering | `validateHost` / `validateSshUser` | mitigate | Shell metacharacters, schemes, ports and whitespace are rejected with a dedicated code before any other check, so a hostile host string never reaches phase 2's command templates (PITFALLS.md #9) |
| T-1-14 | Elevation of Privilege | `validatePassword` | mitigate | 12-character minimum plus a common-password denylist and an identifier-equality check; no composition rules that push users toward predictable patterns |
| T-1-15 | Information Disclosure | `buildActivityEvent` metadata | mitigate | Recursive forbidden-key check plus `SecretValue` instance rejection raises `SensitiveMetadataError` at construction time, so AUTH-04's "sin incluir el password" is structurally enforced rather than reviewed |
</threat_model>
