<interfaces>
Foreign-key facts that fix the delete order (verified against the committed schema — note this
CORRECTS 03-RESEARCH.md's Pitfall 5, which lists credentials before servers):
  servers.credential_id -> credentials.id, ON DELETE **no action** (apps/control-plane/src/db/schema/servers.ts)
  discovery_snapshots.server_id -> servers.id, ON DELETE **cascade** (migration 0003, plan 03-03)
  activity_events.entity_id has **no FK at all** (deliberate: the audit trail outlives the entity)
Therefore the only order that satisfies every constraint is:
  1. write `server.deleted`  2. DELETE FROM servers (cascades discovery_snapshots)  3. DELETE FROM credentials
Deleting credentials first would violate the still-present `servers.credential_id` reference.
</interfaces>

    1. `select ... from servers where id = $serverId` with `.for('update')` -> NOT_FOUND when absent.
    2. `if (row.status === 'CONNECTING') return { ok: false, code: 'SERVER_BUSY', ... }` (D-11), so an

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| destructive admin action -> persisted state | A deletion is irreversible; it must be confirmed, audited and atomic |
| in-flight connect job -> row being deleted | A job holding the old row id must not resurrect state after the delete |

## STRIDE Threat Register

| Threat ID | Category | Description | Asset | Severity | Disposition | Mitigation (task) |
|---|---|---|---|---|---|---|
| T-3-09 | Repudiation | A server disappears with no record of who removed it or what it was | audit trail | high | mitigate | Task 2 writes `server.deleted` before the rows are removed, inside the transaction; Task 1 asserts the event survives |
| T-3-11 | Information Disclosure | The encrypted credential or the discovery snapshots of a deleted server survive and keep exposing host facts | `credentials`, `discovery_snapshots` | high | mitigate | Same-transaction credential delete + plan 03-03's FK cascade; asserted by row counts |
| T-3-28 | Tampering | An accidental or coerced deletion removes the wrong server | `servers` | high | mitigate | D-12's exact, case-sensitive, untrimmed name confirmation against the live row, asserted for case and whitespace variants |
| T-3-06 | Tampering | A concurrent connect job writes status/fingerprint onto a row mid-deletion | `servers` | high | mitigate | `SELECT ... FOR UPDATE` + the D-11 `SERVER_BUSY` rejection |
| T-3-29 | Denial of Service | A partial delete leaves a server row referencing a removed credential (or vice versa), breaking every later connect | `servers`/`credentials` integrity | medium | mitigate | Single transaction plus the FK-driven delete order (servers before credentials), asserted by the "other server intact" and orphan-count cases |
</threat_model>
