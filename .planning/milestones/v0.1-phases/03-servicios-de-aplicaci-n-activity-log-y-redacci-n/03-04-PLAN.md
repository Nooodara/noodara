      input: { kind: 'private_key'; privateKey: string; passphrase?: string } | { kind: 'password'; password: string }
      - password input -> { ok: true, type: 'ssh_password', encryptedValue, keyVersion: key.version }, envelope plaintext is the bare password string
      - private key without passphrase -> { ok: true, type: 'ssh_private_key', ... }, envelope plaintext is JSON with exactly one key: `privateKey` (assert `'passphrase' in JSON.parse(decrypted)` is false)
      - private key with passphrase -> envelope plaintext is JSON `{ privateKey, passphrase }`
      - a malformed private key ('not-a-key') -> { ok: false, code: 'INVALID_CREDENTIAL', message } and nothing is encrypted
      - an RSA key below 2048 bits -> { ok: false, code: 'INVALID_CREDENTIAL' } with the message coming from `loadPrivateKey`, not from a locally written rule
      - a wrong passphrase for an encrypted key -> { ok: false, code: 'INVALID_CREDENTIAL' } (loadPrivateKey's `kind: 'auth'` variant is a validation failure at registration time, not an AUTH_FAILED connection outcome)

      - the returned object has no field holding the plaintext (assert the JSON of the result does not contain the input secret)

    decodeCredential(row, masterKeys)
      row: { type, encryptedValue, keyVersion }
      - ssh_password row -> { kind: 'password', password: SecretValue } and `revealSecret(password)` equals the original
      - ssh_private_key row without passphrase -> { kind: 'private_key', privateKey: SecretValue } with `'passphrase' in result` false
      - ssh_private_key row with passphrase -> both fields present, both SecretValue, passphrase uses SecretKind 'ssh_private_key' (SecretKind is not widened this phase)
      - a row encrypted under `masterKeys.previous` still decodes when `previous` is supplied
      - a tampered envelope throws (SecretTamperError propagates — this is a bug/infra failure, not an expected result)
      - `String(result)` / `JSON.stringify(result)` never contains the plaintext (SecretValue's own guard)

    currentKeyVersion(handle)
      - returns `max(key_version)` over `credentials`, or 1 when the table is empty
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin input -> credentials table | Raw key/password material crosses into encrypted storage; it must be validated then immediately enveloped |
| credentials row -> SSH adapter | Stored ciphertext is decrypted into SecretValue for the lifetime of one operation |
| service result -> API caller (phase 4) | `ServerView` is the only thing that crosses back out |

## STRIDE Threat Register

| Threat ID | Category | Description | Asset | Severity | Disposition | Mitigation (task) |
|---|---|---|---|---|---|---|
| T-3-01 | Information Disclosure | A service result carries the credential (id, envelope, or plaintext) back to a caller | service results, future API responses | high | mitigate | Task 3's allowlist projection + the key-list and pollution tests; `credentialId` is structurally absent |
| T-3-03 | Information Disclosure | Plaintext key/password is stringified into a log line or an error message | logs, error bodies | high | mitigate | Task 2 keeps plaintext inside `SecretValue`/the envelope only, registers nothing itself, and asserts `JSON.stringify(result)` is clean; end-to-end proof is plan 03-10's canary |
| T-3-10 | Tampering | A weak or malformed key is persisted and only fails at first connect | credential quality, connect reliability | high | mitigate | Task 2 calls `loadPrivateKey` before encrypting; grep criterion forbids locally duplicated key rules |
| T-3-21 | Information Disclosure | A key passphrase is stored outside the envelope (a separate column, or plaintext JSON alongside) | `credentials` row | high | mitigate | Task 2's D-15 JSON-inside-one-envelope shape, with the "passphrase key absent when omitted" assertion |
| T-3-22 | Information Disclosure | A decrypted credential stays registered in `appRedactor` forever because a service registers it manually | process memory / redactor registry | medium | accept (documented) | Ownership stays with `@noodara/ssh`'s session lifecycle (RESEARCH Pitfall 3); credential-store deliberately registers nothing — enforced by the file header and reviewed in plan 03-08's `finally`-close test |
</threat_model>
