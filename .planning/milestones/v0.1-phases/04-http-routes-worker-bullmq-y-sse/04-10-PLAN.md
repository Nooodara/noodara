<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client query params → SQL | `limit` and `cursor` shape a database query |
| audit store → response | Activity metadata written across the whole system becomes client-visible |
| unauthenticated network → `/health` | The one route that answers without a session |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-11 | Information Disclosure | activity items | mitigate | The read selects an explicit ten-column list (no `select()`), and `metadata` is returned exactly as `writeActivityEvent` redacted it on write; a test asserts the item key set |
| T-4-39 | Tampering | cursor input | mitigate | `decodeActivityCursor` validates the timestamp and uuid and returns a result; an invalid cursor is a 400, never a 500 and never a silently unfiltered page |
| T-4-40 | Denial of Service | `limit` abuse | mitigate | `limit` is a coerced integer bounded 1–200 by the Zod schema before the query is built; the query always uses `limit + 1`, never an unbounded scan |
| T-4-12 | Information Disclosure | `/api/config` | mitigate | Only the 16-hex truncated SHA-256 of the master key is exposed — the same one-way digest Phase 1 logs at boot; a test asserts the raw key does not appear in the body |
| T-4-41 | Information Disclosure | `/health` (unauthenticated) | mitigate | The body carries only the version and three `pass`/`fail` literals — no connection string, no error text, no key names; each check maps any failure to `'fail'` without propagating its message |
| T-4-42 | Denial of Service | `/health` under a hanging dependency | mitigate | Each check is individually time-bounded to ~2s and can never throw out of the handler, and the worker check uses `SCAN` with a bounded `COUNT` rather than `KEYS` |
</threat_model>
