<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dead worker → server state | A process crash leaves persisted state mid-transition and must not be trusted as final |
| job payload actor → activity attribution | The actor recorded on the recovery event originates in a Redis-stored job payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-09 | Repudiation | abandoned CONNECTING row | mitigate | `failInFlightConnection` transitions to `ERROR` with `CONNECTION_LOST` and writes one `server.connection_attempted` failure event, so every abandoned attempt leaves an audit record instead of vanishing |
| T-4-23 | Tampering | clobbering a finished attempt | mitigate | The `SELECT ... FOR UPDATE` plus the `status !== 'CONNECTING'` skip makes recovery a no-op against a result that already landed, so a late stall signal cannot overwrite a genuine `CONNECTED` |
| T-4-24 | Spoofing | actor attribution on recovery | mitigate | The actor is carried through from the original job payload, which Plan 04-07 Zod-validates on consume and which never contains anything but `{ type: 'user', id }`; the service computes `actorId` with the same expression the other five services use |
| T-4-25 | Information Disclosure | recovery activity metadata | mitigate | Metadata is `{ reason }` with a value from a fixed two-member union — no host, user, credential or error text; `buildActivityEvent`'s forbidden-key scan still applies |
</threat_model>
