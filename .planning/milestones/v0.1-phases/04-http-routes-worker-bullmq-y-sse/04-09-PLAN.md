    - A message on the channel is written to every registered stream as `event: <type>\ndata: <the raw message>\n\n`
    - A message whose `type` is not one of the two known event types is dropped without writing anything (a foreign publisher on a shared Redis cannot inject arbitrary SSE frames)
    - A message that is not valid JSON is dropped and logged at warn, and later valid messages still fan out

    - A stream whose `write` throws is removed from the registry and does not prevent the remaining streams from receiving the same message
    - `size` reflects the number of registered streams, and `add` beyond `maxConnections` is rejected by the caller checking `size` first (the broadcaster exposes the number; the route owns the 503)
    - `closeAll()` calls `end()` on every registered stream, empties the registry and unsubscribes
    - A subscriber connection `error` event logs at warn and never throws
  </behavior>

Then create `apps/control-plane/src/events/sse-broadcaster.ts`:
- `createSseBroadcaster({ subscriber, logger, maxConnections })` holds a `Set<SseStream>` and returns the `SseBroadcaster` port.
- `start()` registers `subscriber.on('message', handler)`, `subscriber.on('error', warn-log)`, then `await subscriber.subscribe(SERVER_EVENTS_CHANNEL)`.
- The handler parses the message, checks `type` against the two known values, and writes `event: ${type}\ndata: ${message}\n\n` to each stream, forwarding the original message string rather than re-serialising the parsed object (one serialisation, one shape, no drift between what the publisher sent and what the browser reads).
- Wrap each per-stream `write` in its own try/catch: one dead socket must never stop the others from getting the event. Remove the failing stream from the set.
- `closeAll()` ends every stream, clears the set and `await subscriber.unsubscribe(SERVER_EVENTS_CHANNEL)`. It is idempotent.
- `SseStream` is a narrow structural interface (`{ write(chunk: string): void; end(): void }`), not Fastify's `FastifyReply` or Node's `ServerResponse` — that is what makes this file unit-testable with plain objects and keeps the fan-out logic independent of the HTTP layer.
- No replay, no buffer, no `Last-Event-ID` handling (D-05, explicitly deferred): a reconnecting client resynchronises with `GET /api/servers`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Redis channel → API process | Any writer to a shared Redis can publish on the channel the API fans out verbatim |
| long-lived stream → session lifetime | An SSE connection outlives the request that authenticated it |
| open sockets → process resources | Each stream holds a socket, a timer and a registry entry for as long as the client wants |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-02 | Elevation of Privilege | live stream after logout/revocation | mitigate | The heartbeat re-resolves the session every interval and ends the stream when it is gone, bounding the exposure window to one interval (~15s in production); asserted by a revocation test (D-06, ASVS V3) |
| T-4-01 | Spoofing | `/api/events` | mitigate | Registered inside the guarded scope, so `requireSession` 401s before any stream is opened; asserted by an anonymous-request test |
| T-4-05 | Information Disclosure | SSE frame payload | mitigate | Frames carry the `ServerView` produced by `toServerView`'s 27-field allowlist, asserted key-for-key on a received frame; the adapter never re-projects, so there is exactly one allowlist |
| T-4-36 | Tampering / Injection | foreign message on the channel | mitigate | The broadcaster drops any message whose `type` is not one of the two known events and any message that fails to JSON-parse, so a third-party writer on a shared Redis cannot inject arbitrary SSE frames into an admin's browser |
| T-4-06 | Denial of Service | unbounded streams | mitigate | `NOODARA_SSE_MAX_CONNECTIONS` checked before hijack, answering 503 with `Retry-After`; each stream's timer is `unref`ed and removed on client close |
| T-4-37 | Denial of Service | shutdown deadlock | mitigate | Streams are ended in `preClose`, proven by a test that asserts `app.close()` resolves with a stream still open — the exact failure Fastify's drain phase would otherwise cause |
| T-4-08 | Denial of Service | Redis outage | mitigate | `broadcaster.start()` failure is caught and warn-logged in `onReady`; the route still accepts connections and heartbeats, and ioredis `autoResubscribe` restores fan-out on reconnect |
| T-4-38 | Information Disclosure | publish-failure logs | mitigate | The adapter logs through pino's `err` serializer with a fixed message; no Redis URL, host or port is interpolated into a log line |
</threat_model>
